# 03 · 影视与音乐源与播放体验

> **这份文档讲什么**：影视采集源、音乐音源的**长期可靠性**，源健康面板怎么从「一张状态表」
> 变成「能回答问题的诊断工具」，以及**播放/听歌体验**还差哪些。
>
> **写给谁看**：站长本人（不懂技术也能看懂结论和优先级）+ 后续接手的执行 Agent（照章节就能干活）。
>
> **基线**：`main` @ `f4d4af8`（2026-10-10 影音源修复已上线）。
> 相关既有文档：`docs/source-health.md`（设计）、`docs/media-source-repair.md`（本轮修复）、
> `docs/interface-inventory.md`（逐条实测结论）、`docs/removed-features.md`（哪些源已删，不要加回）。
>
> **优先级口径**（与 `00-总览与阅读指引.md` 一致）：
> **P0** = 影响「看起来是不是个完整产品」；**P1** = 影响「用起来顺不顺」；**P2** = 打磨与扩展。
> 工作量：**S** ≈ 半天内，**M** ≈ 1–2 天，**L** ≈ 3 天以上。

| --- | --- | --- | --- |
| 1 | **给普通用户看只读版源状态 + 单源一键重测** | 源健康中心做了，但藏在「更多」里、只有管理员能看；站长排查一次要翻半天 | 3.2 / 3.6 |

- ❌ 不要为了凑数量加回已确认失效的源（ffzy / dytt / zuid / lzi / jszy / hongniu / jyzy / dbzy /

## 2. 源可靠性的长效机制

### 2.1 定期自动探活（P1，工作量 M）

**现状**：只有管理员手动点「刷新」（`?refresh=1`）才会探测。没人点，面板就一直是空/过期。

**为什么不能直接加个 Cron 就完事（重要坑）**

现在的健康缓存是**进程内的 `createHealthStore()`**（`backend/src/lib/sourceHealth.js`），
而 Cloudflare Workers 会横向开多个实例（isolate），**每个实例各有一份缓存**。
所以「定时任务探一次」只会把结果写进**跑定时任务的那一个实例**，
搜索请求落到别的实例时**照样看不到这份结果**——定时探活等于白跑。

**建议做法（两步，缺一不可）**

1. **把探测结果落到数据库**（新建迁移，例如 `supabase/migrations/20261011000016_source_health.sql`）：
   建一张 `source_health_snapshots` 表，字段建议
   `key / kind / status / latency_ms / error / capabilities(jsonb) / checked_at / probe_kind`，
   并保留最近 N 条历史（后面第 3.1 节的「可用率趋势」直接复用同一张表）。
   ⚠️ 只新增迁移，**不要改历史迁移**（项目铁律）。
2. **加一个 Cron**（`backend/wrangler.toml` 的 `[triggers] crons`，现在只有 GitHub Star 同步的
   `"*/5 2-3 * * *"`），例如每 30 分钟跑一次，在 `backend/src/index.js` 的 `scheduled()` 里
   调用 `probeMovieSources(env)` / `probeMusicSources(env)` 并写入快照表。

**搜索侧怎么用**：在 `backend/src/lib/sourceHealth.js#createHealthStore` 的
`allowProbe: false` 分支里，当**本地缓存缺失或过期**时，**回退读数据库快照**
（而不是像现在这样直接返回空 `sources`）。这样：

- 访客仍然**不触发任何上游探测**（守住 `docs/source-health.md` 第 5 节的硬约束）；
- 定时任务的结果能被**所有实例**共用；
- 「冷启动安全」不破：快照也没有时，`rankSources` 仍然不剔除任何源。

**涉及文件**

| 动作 | 文件 |
| --- | --- |
| 新建快照表迁移 | `supabase/migrations/20261011000016_source_health.sql`（新增） |
| 写快照 + 读快照回退 | `backend/src/lib/sourceHealth.js` |
| 注册 Cron 与调度分支 | `backend/wrangler.toml`、`backend/src/index.js` |
| 文档同步 | `docs/source-health.md`、`docs/progress.md` |

**优先级 P1**（决定了「源状态是不是一直准」，是第 3 节所有面板功能的地基）。

### 2.2 探测结果如何影响搜索排序（P1，工作量 S）

**现状**：已经做了「跳过 `down`、`degraded` 排后」（`rankSources`，被
`backend/src/lib/fetchers.js#searchMaccmsAll` 与 `#fetchMusicMeta` 调用）。
**但要守住两条铁律**（`docs/progress.md` 2.31 已明确）：

1. 健康数据缺失时**不剔除任何源**（冷启动安全）；
2. 健康只调整「哪些源参与、以什么顺序发起」，**不改最终的相关度排序**。

**建议补充（小改，收益明显）**

- **探测词不要只有一个**：现在是固定词 `测试`（中文）/ `test`（英文）。
  建议改成**固定 2–3 个真实片名/歌名**（例如影视用 3 部知名片），
  避免某个源「刚好没有『测试』这部片」被误判成 `degraded`。
  位置：`backend/src/lib/sourceHealth.js` 的 `PROBE_KEYWORD_CN` / `PROBE_KEYWORD_EN`。
- **探测口径对齐验收口径**：影视探活目前是「搜索 + 详情 + 有可播放地址」，
  建议再加一步「取首个 ts 分片看是否 206」（与 `docs/interface-inventory.md` 的收录口径一致）。
  代价是探测变慢，建议**只让 Cron 走全量口径**，手动刷新走轻量口径。
  位置：`backend/src/lib/sourceHealth.js#probeOneMaccms`。

**优先级 P1**（探测准不准，直接决定搜索会不会误跳过好源）。

### 2.3 连续失败几次自动降级 / 下线（P1，工作量 M）

**现状**：一次探测 `down` 就跳过该源，下一次探测好了又回来。没有「连续失败」的概念，
所以偶发抖动和真下线分不开。

**建议规则（建议值，可调）**

- 连续 **2 次** `down` → 标记 `degraded`（仍参与搜索，但排最后）；
- 连续 **3 次** `down` → 标记 `down`（搜索跳过）；
- 恢复 **1 次** `ok` → 立刻恢复 `ok`（不搞「需要连续成功 N 次」，避免误伤）。

**实现要点**

- 判定需要**跨探测的历史**，所以依赖 2.1 的 `source_health_snapshots` 表；
  在 `backend/src/lib/sourceHealth.js` 里加一个纯函数
  `applyFailurePolicy(recentStatuses, current)`，便于离线单测。
- **绝不自动改 `DEFAULT_VOD_SOURCES`**（源码里的源列表）：自动降级只影响「这次搜索用不用它」，
  改源码仍然是站长手动决定。这条要写进注释，防止后续 Agent 理解成「自动删源」。

**涉及文件**：`backend/src/lib/sourceHealth.js`、`backend/src/lib/fetchers.js`、
`backend/tests/run.mjs`（补纯离线用例）、`docs/source-health.md`。

**优先级 P1**。

### 2.4 源权重（P2，工作量 S）

**现状**：源顺序就是 `DEFAULT_VOD_SOURCES` 的书写顺序 + 健康分档，没有权重概念。

**建议**：先做**静态权重**（够用），不要一上来做动态学习。

- 在 `backend/src/lib/maccms.js` 的源定义里加可选字段 `weight`（默认 1），
  `rankSources` 排序时把 `weight` 作为同档内的次序依据；
  站长想「优先用搜索最快的源」直接改数字即可。
- 音乐侧同理（`backend/src/lib/meting.js` 的实例/平台、`fetchers.js` 里 GD 的 source 列表）。
- **不要**用「历史可用率」自动算权重（样本太少、波动大，容易把好源排后）。
  若以后数据够了再考虑，且必须离线可单测。

**涉及文件**：`backend/src/lib/maccms.js`、`backend/src/lib/sourceHealth.js`（`rankSources`）、
`backend/src/lib/fetchers.js`。

**优先级 P2**。

## 3. 源健康面板的改进

> 目标：把「一列状态」升级成能**正面回答用户问题**的诊断面板——
> 「为什么这部片搜不到 / 这首歌放不出来 / 是哪个源的问题」。

### 3.1 历史可用率趋势（P1，工作量 M）

**现状**：只有「最近一次探测」的快照（`generated_at`），没有历史。

**建议**

- 数据源：复用 2.1 的 `source_health_snapshots` 表，后端加
  `GET /api/sources/health/history?key=<源>&hours=24`（管理员）。
- 展示：每个源一行后面加一条**迷你折线/色块条**（近 24h 每 30 分钟一格：绿=ok / 黄=degraded / 灰=down），
  以及「近 24h 可用率 96%」这样的数字。
- **不引入图表库**：色块条用纯 CSS（`flex` + 背景色）即可，
  避免违反 `docs/progress.md` 第 4 节的「重型库必须按路由动态 import」规范。

**涉及文件**：`backend/src/routes/movies.js`（新增 handler）、`backend/src/router.js`、
`frontend/src/routes/SourceHealth.jsx`、`frontend/src/lib/api.js`、`frontend/src/styles/global.css`。

**优先级 P1**（这是把面板从「瞬时观测」变成「可信赖的观测」的关键）。

---

### 3.2 单源一键重测（P0，工作量 S）

**现状**：只能整体刷新（`?refresh=1` 重探全部 14 个源），慢且浪费配额
（音乐源有 5 分钟 50 次的限频）。

**建议**

- 后端新增 `POST /api/sources/:key/probe`（`requireAdmin`）：
  只探一个源，返回该源记录，并**合并进现有缓存**（不整体覆盖）。
  实现上把 `sourceHealth.js` 里私有的 `probeOneMaccms` / `probeGdstudio` / `probeMeting` 等
  整理成一个按 `key` 分发的 `probeOneByKey(env, key)`。
- 前端每行右侧加一个「重测」小按钮，只转这一行的圈；失败原因就地展开。

**涉及文件**：`backend/src/lib/sourceHealth.js`（导出单源探测）、
`backend/src/routes/movies.js` 或新建 `backend/src/routes/sources.js`、
`backend/src/router.js`、`frontend/src/routes/SourceHealth.jsx`、`frontend/src/lib/api.js`。

**优先级 P0**（成本极低、日常排查最常用，属于「面板是不是能用」的门槛功能）。

### 3.3 失败原因分类（P1，工作量 S）

**现状**：`error` 是一句自由文本（如「详情接口验证失败：HTTP 502」），人读得懂但**不能统计**。

**建议**：在 `finalizeRecord`（`backend/src/lib/sourceHealth.js`）里补一个**枚举化的 `error_kind`**：

| `error_kind` | 含义 | 用户该怎么做 |
| --- | --- | --- |
| `timeout` | 探测超时 | 大概率是网络/限频，稍后重测 |
| `http_error` | 上游返回 4xx/5xx | 源站问题，可考虑下线 |
| `bad_response` | 返回结构非法（非 JSON 等） | 源站改了接口 |
| `empty_result` | 搜索空结果 | 探测词问题或源库变小 |
| `no_play_url` | 有结果但取不到播放地址 | 典型「降级」 |
| `trial_only` | 只有 30 秒试听 | 正常，不算故障 |
| `rate_limited` | 429 | 上游限流（iTunes 常态） |

前端按 `error_kind` 分组统计（「3 个源超时 / 1 个限流」），比一堆红字有用得多。

**涉及文件**：`backend/src/lib/sourceHealth.js`（`judgeMovieProbe` / `judgeMusicProbe` / `finalizeRecord`）、
`frontend/src/routes/SourceHealth.jsx`、`backend/tests/run.mjs`。

**优先级 P1**。

### 3.4 与搜索失败的关联（P1，工作量 M）

**现状**：搜不到片子时，用户只看到一句「未找到匹配的剧集」，
**完全不知道是因为 3 个源刚好挂了**。这是采集型产品最容易被质疑的点。

**建议**

1. **搜索时记录「因为健康被跳过/后置的源」**：
   在 `backend/src/lib/fetchers.js#searchMaccmsAll` 里，把 `rankSources` 剔除的源
   收集为 `skipped_sources`，随 `fetchMovieMeta` 的结果一起返回
   （音乐侧 `fetchMusicMeta` 同理，返回 `skipped_sources`）。
2. **前端空态/提示里说清楚**：
   `frontend/src/routes/Movies.jsx` 的结果提示区（现在渲染 `candNote`）里，
   当 `skipped_sources.length > 0` 时追加一句：
   「本次有 3 个源因暂时不可用被跳过（查看源状态）」，并给一个跳 `/sources` 的链接。
   音乐侧同理改 `frontend/src/routes/Music.jsx` 的 `searchNote` 区域。
3. **面板侧反向链接**：`SourceHealth.jsx` 每个 `down` 源后面加一句
   「可能影响《…》这类搜索」——用最近一次搜索的跳过记录生成，数据量小时甚至可以省略，
   第 1、2 步已经解决 80% 的痛点。

**涉及文件**：`backend/src/lib/fetchers.js`、`backend/src/routes/movies.js`、`backend/src/routes/music.js`、
`frontend/src/routes/Movies.jsx`、`frontend/src/routes/Music.jsx`。

**优先级 P1**（这是「源健康」这个功能对站长之外的人产生价值的地方）。

### 3.5 导出与通知（P2，工作量 M）

**现状**：面板只在页面上看得到，源挂了站长不知道。

**建议**

- **导出**：`SourceHealth.jsx` 加一个「复制为文本 / 导出 JSON」按钮（纯前端即可，无需新接口），
  方便贴给别人排查。
- **通知**：复用现成的通知中心（`backend/src/routes/notifications.js`，已有 `link_broken` / `system` 类型）。
  在 Cron 探活后（2.1），若某源从 `ok` 变 `down` 且**连续 2 次**，
  写一条 `type='system'` 的通知（标题如「采集源「豪华资源」连续 2 次不可用」）。
  ⚠️ **必须去重**：同一源在恢复前只告警一次，否则通知中心会被刷屏
  （可参考 `checkLinks` 里「已有未读告警就跳过」的做法）。

**涉及文件**：`backend/src/routes/notifications.js`、`backend/src/lib/sourceHealth.js`（或 `backend/src/index.js` 的 scheduled）、
`frontend/src/routes/SourceHealth.jsx`。

**优先级 P2**。

### 3.6 面板该放哪 + 普通用户只读版（P0，工作量 S）

**现状**：`/sources` 藏在「更多」下拉里，且**只有管理员能看到入口**
（`frontend/src/components/Layout.jsx` 第 107 行 `{isAdmin && ...}`）。
普通用户遇到「搜不到」，没有任何地方能自查。

**建议（导航位置）**

## 4. 采集源扩充方法论（P2，工作量 S；流程本身是规范）

**现状**：源是「一次性实测后写死」在 `backend/src/lib/maccms.js#DEFAULT_VOD_SOURCES` 里的，
新源来了靠人肉测。`docs/interface-inventory.md` 已经沉淀了「只记录结论」的格式。

```
候选收集 → 逐条实测 → 与已有清单去重 → 结论写回 interface-inventory.md → 只集成可播的 → 登记到 DEFAULT_VOD_SOURCES
```

**候选来源（值得评估的类型）**

| 类型 | 说明 | 评估要点 |
| --- | --- | --- |
| 苹果CMS v10 采集站（`/api.php/provide/vod/`） | 现有 7 个都是这类 | 同质化严重，重点看**片库差异**（有没有别人没有的片） |
| 自建/聚合型 API | 需自部署或 key | 默认**不引入**（见 `docs/removed-features.md`） |
| 公开元数据（Cinemeta / Bangumi / Kitsu） | 只补海报评分，不提供播放 | 已集成，不属「源扩充」 |

**硬指标（不满足任何一条即不收录）**

1. **搜索**：固定 5 部片（覆盖电影/剧集/动漫/冷门/新片）全部有结果；
2. **详情**：`ac=detail` 返回 `vod_play_url`，且至少一条线路含 m3u8 直链；
3. **首个分片**：master → 变体 → **首个 ts 分片 HTTP 206**；
4. **延迟**：搜索 < 1.5s、片源 < 1.5s（超过就拖垮整体搜索预算）；
5. **命中率**：**5/5 才收录**（`ruyi` 3/5 就是因此被拒）。

**登记要求**：新源必须同时写入
`backend/src/lib/maccms.js`（`DEFAULT_VOD_SOURCES` + 必要的 `ANIME_CLASS_IDS`）与
`docs/interface-inventory.md`（含实测日期、5 部片名、结论）。

**涉及文件**：`backend/src/lib/maccms.js`、`docs/interface-inventory.md`、`docs/progress.md`。

**顺带修一处文案不一致（P2，S）**：`frontend/src/routes/Movies.jsx` 的页头副标题写的是

**不要在文案里硬编码源数量**——改为「在全部可用采集源里搜索播放」，
或者由接口返回的源数量动态渲染，避免以后增删源时又对不上。

**优先级 P2**（不紧急，但**每次加源都必须照这个流程**，否则会重新引入死源）。

## 5. 「4K / 高音质」的现实边界（P0，工作量 S；属于「如实标注」）

### 5.1 影视清晰度：不能承诺 4K

**事实**：苹果CMS 采集源返回的 `vod_play_url` 只有 **m3u8 / mp4 直链字符串**，
接口里**没有可靠的清晰度或码率字段**。`backend/src/lib/maccms.js#normalizeVod`
只保留可播直链，不解析分辨率。

**能做**

- 如实展示源站自己标的备注（`vod_remarks`，已存为 `movie_titles.remarks`，
  详情页 `MovieView.jsx` 已渲染为 `.remark-chip`），但**必须标注是「源站标注，未经验证」**。
- 播放器侧显示实际视频尺寸（`<video>` 的 `videoWidth/videoHeight`，hls.js 起来后可得），
  这是**唯一可信的清晰度信息**。

**不能承诺**

- ❌ 不能写「4K / 蓝光 / 超清」当卖点；
- ❌ 不能按「清晰度」给线路排序（没有数据）。

**建议文案（详情页线路区）**：
> 「清晰度以实际播放为准；来源站标注仅供参考。」

**涉及文件**：`frontend/src/routes/MovieView.jsx`、`frontend/src/components/MoviePlayer.jsx`。

**优先级 P0**（涉及「不许虚假宣传」，是底线而非优化）。

---

### 5.2 音乐音质：FLAC 完整曲 vs 30 秒试听

**事实**

- **完整曲**：GD音乐台网易云 `br=999` → 实测 56MB FLAC / 1607kbps（`docs/interface-inventory.md`）；
  Meting 网易云/咪咕 → 302 端点，跟随跳转即得音频。
- **30 秒试听**：iTunes / Deezer 只给 preview，**永远不是完整曲**。
- **会过期的直链**：GD 是带时间戳的签名地址，播放失败时靠
  `POST /api/music/stream` 重新解析（`backend/src/routes/music.js#resolveMusicStream`）。

**前端如实标注的现状与缺口**

| 位置 | 现状 | 缺口 |
| --- | --- | --- |
| `frontend/src/routes/Music.jsx` 搜索结果行 | 有「无损 / 完整音轨 / 试听 / 待解析」四态 | 基本够用 |
| `frontend/src/routes/MusicView.jsx` 详情页 | 有 `quality-tag`（试听片段 / 无损·完整音轨） | ⚠️ 徽标文案固定写「无损 / 完整音轨」，**`quality=full` 但没有 bitrate 时也这么写**，不够严谨 |
| `frontend/src/components/MiniPlayer.jsx` 底部播放条 | **没有任何音质标注** | 建议加一个小「试听」角标 |
| `frontend/src/routes/MusicPlayer.jsx` 沉浸页 | 有 quality-tag | 同上，按实际字段分级 |

**建议统一的三级文案**（后端已有字段可直接判断）

1. `format === 'flac'` 或 `bitrate >= 900` → **「无损 · FLAC · 1607kbps」**；
2. 有直链但码率未知 → **「完整音轨」**（**不要**写「无损」）；
3. `quality === 'preview'` 或只有 `preview_url` → **「试听 30 秒」**。

**涉及文件**：`frontend/src/routes/MusicView.jsx`、`frontend/src/routes/MusicPlayer.jsx`、
`frontend/src/components/MiniPlayer.jsx`、`frontend/src/routes/Music.jsx`。

**优先级 P0**（与影视清晰度同属「不许虚假宣传」底线；`00-总览` 已列入「明确不要做」）。

## 6. 存量死链自愈（P1，工作量 M）

**现状**：2026-10-10 已上线 `POST /api/movies/:id/refresh-source`
（`backend/src/routes/movies.js#refreshMovieSource`），逻辑很稳：
先按原 `source_key + source_vod_id` 回源，不行再用标题重搜，
并且必须过 `pickBestMovieCandidate` 的可信阈值（`RESOLVE_MAX_RELEVANCE = 3`）才写库。
**但只能一条条点**，且只在详情页/重匹配按钮上出现。

**背景数据**：线上 `resources(type='movie')` 共 7 条，`source_key` 是
`dytt` / `jszy` / `lzi`（**都已在 2026-10-09 下线**），其中 2 条直链是 403/404 死链。

**建议的三种后续用法（按建议顺序做）**

1. **批量重匹配接口**（P1，M）
   - 新增 `POST /api/movies/refresh-sources`（`requireAdmin` 或站长本人），
     body 支持 `{ ids: [...] }` 或 `{ only_broken: true, limit: 10 }`；
   - **逐条串行**（不要并发打采集源），每条返回 `{ id, title, ok, matched, reason }`；
   - **必须复用** `pickBestMovieCandidate`，**绝不放宽阈值**；
   - 前端在 `frontend/src/routes/Movies.jsx` 加一个「修复失效片源」按钮，
     跑完显示「成功 3 / 跳过 2 / 失败 1」的明细。
   - ⚠️ 保持「不自动批量改库」的既有原则：由站长**主动点击**才跑，不做后台静默改写。

2. **定时巡检**（P1，M，依赖 2.1 的快照/记录能力）
   - 每天一次，用 `HEAD`/`Range: bytes=0-0` 探一下已入库的影视直链
     （可复用 `backend/src/lib/linkcheck.js#checkLink` 的思路）；
   - 发现失效 → 写一条通知（`type='system'`，标题「《…》片源可能已失效」），
     **不自动改库**；
   - ⚠️ `checkLinks` 目前**只扫 `type='video'`**（`backend/src/routes/notifications.js`），
     需要扩展成 `type in (video, movie, music)`，并注意 m3u8 要带 `Range` 才准。

3. **失效自动标记**（P2，S）
   - 在 `resources.metadata` 里加 `url_stale: true`（音乐侧已有类似字段
     `url_stale`，见 `backend/src/routes/music.js#getMusic`），
     前端在列表/详情页显示「源可能已失效」的小标记，点一下触发重匹配。
   - 影视侧目前是**前端现算**（`MovieView.jsx` 的 `urlStale`），
     建议下沉到后端返回，避免前后端两套判定逻辑漂移。

**涉及文件**：`backend/src/routes/movies.js`、`backend/src/routes/notifications.js`、
`backend/src/lib/linkcheck.js`、`frontend/src/routes/Movies.jsx`、`frontend/src/routes/MovieView.jsx`、
`frontend/src/lib/api.js`。

**优先级 P1**（`00-总览` 列为 P1 第 7 项）。
