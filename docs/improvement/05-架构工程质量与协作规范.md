## 0. 先看结论（站长 30 秒版）

| 问题 | 现在 | 建议 | 见 |
| --- | --- | --- | --- |
| 改代码会不会影响线上 | 会。推到 `main` 几分钟后自动上线 | 小改照旧；**大改先开分支**，确认再合并 | §7 |

| 多个 Agent 一起改 | 全靠一份 `progress.md` 接力 | 一个任务一个目录 / 分支，零共享写入 | §7 |

> **站长不需要记技术细节**：只要记住一句话——
> **"小改动直接让 Agent 在 main 上做；大改动必须先开草稿本（分支），我点头后再上线。"**
> 剩下的是 Agent 的纪律。

### 1.2 一次请求的完整路径（四条典型链路）

**A. 访客读一篇公开博客（不登录）**

```
浏览器 GET /posts/xxx
  → Pages 返回 SPA 的 index.html + JS
  → JS 调 GET https://api.xuguochen.de5.net/api/posts/:id（无 token）
  → auth.js 发现 PUBLIC_MODE="true" 且路径在白名单 → 构造「访客上下文」
      user.id = 站长 owner 的 id（只用于限定范围），isGuest=true / isAdmin=false
  → 路由必须再叠加公开过滤：status=published AND is_public=true，否则 404
  → Worker 用 service_role 直连 PostgREST 取数（⚠ RLS 不替 Worker 过滤）
  → 返回 JSON → 前端渲染
```

**B. 站长写一篇文章（登录）**

```
浏览器已持有 Supabase JWT
  → POST /api/posts，带 Authorization: Bearer <JWT>
  → auth.js verifyJwt → 查 user_profiles 拿角色 → 构造登录上下文
  → 路由写入时强制 user_id = 当前用户
      （管理员只有 ?all=true 的**读**权限，写操作不跨用户）
  → 落库 Supabase
```

**C. 影视检索与播放（多源聚合 + 代理）**

```
POST /api/movies/search  → lib/fetchers.js 并发查多个采集源
     ↳ 读「源健康缓存」rankSources：跳过已知 down 的源
       （冷启动 / 无健康数据时不剔除任何源，否则首次请求会全空）
     ↳ 元数据补全（豆瓣 / Cinemeta / Bangumi，失败静默）
  → 返回候选（含可播放直链）
播放时 GET /api/vod/proxy?u=<m3u8>
     ↳ 把 m3u8 里的分片地址改写成代理地址，流式透传（支持 Range/206）
     ↳ 用于绕过防盗链 / 非常规端口；按 DISCONTINUITY 去广告
```

**D. 定时任务（GitHub Star 同步 + AI 解读）**

```
Cron "*/5 2-3 * * *" → index.js scheduled()
  → githubStars.scheduledSync()：按页同步站长 GitHub Star 到 resources(type=github)
  → githubAi.analyzePending()：用 Workers AI 解读尚未解读的收藏
```

### 1.3 三个必须记住的架构事实（踩过坑，别再踩）

| 事实 | 后果 | 纪律 |
| --- | --- | --- |
| Worker 用 **service_role** 直连数据库，**RLS 不生效** | 只改中间件白名单 = 没做权限控制，私密数据会被发出去 | **每个读路由都要在查询里显式叠加公开 / 归属过滤**（`backend/src/lib/publicScope.js` 是唯一来源） |
| Pages 部署有**传播延迟**，新资源可能短暂返回 `index.html` | 页面"完全无样式"，或改了文案看不到 | 部署后先轮询资源的 Content-Type 再验收；用部署专属域名先验证 |
| 本地 `wrangler dev` 出网会挂，Node 原生 fetch 不读代理 | 后端联调困难，容易误判"代码坏了" | 纯逻辑走 Node 直连 + 离线单测；接口验证直接打线上 |

## 2. 测试策略

### 2.1 现状：只有"离线单元 + 契约"这一层（60 项全过）

`cd backend && npm run test:unit` 是**纯 Node 脚本**（`backend/tests/run.mjs`），不装任何依赖即可跑，
目前 **60 项全过**。它由三部分组成：

| 部分 | 覆盖什么 | 例子 |
| --- | --- | --- |
| UNIT（纯函数，离线确定性） | 解析器 / 相关度 / 打分 / 直链判定 / 图片类型 / 源健康判定 / 公开读边界 | `titleRelevance`、`normalizeVod`、`isDirectVideoUrl`、`sniffImageType`、`isGuestAllowed` |
| CONTRACT（前端 ↔ 后端契约） | `api.js` 里每个请求路径都能在 `router.js` 找到；每个页面用到的 `api.xxx()` 都真实存在 | 27 个页面文件逐个检查 |
| LIVE（真实联网，需显式开启） | 采集源探活、影视 / 音乐搜索的真实可用率 | 「庆余年」足量且正片在前、「孤勇者」榜首必须是原唱 |

**这层的价值极高、成本极低**：不需要数据库、不需要网络、不需要密钥，任何 Agent 随时能跑，
CI 里也跑了（`quality.yml`）。**必须保持它永远是绿的。**

> 站长视角：这一层相当于"每次改动后自动做一遍算术题"，能挡住绝大多数"改 A 弄坏 B"的低级错误。

### 2.2 建议补的四类测试（按性价比排序）

| 优先级 | 补什么 | 为什么值得 | 怎么做（成本） |
| --- | --- | --- | --- |
| **P0** | **权限边界的"矩阵式"用例** | 项目出过两次真实越权（访客读到站长私密数据、白名单含 `favorites` / AI 接口）。权限是**最容易写错、后果最严重**的地方 | 扩展 `UNIT · 公开读边界`：把 `docs/public-access.md` 的逐路由矩阵**逐条**变成断言（每个读路由 × 访客 / 登录 / 管理员）。纯函数级，零依赖 |
| **P1** | **路由级"冒烟"用例（不连网）** | 现在没有任何东西保证"路由注册顺序 / 参数解析"正确（曾有字面量路径被 `:id` 抢先匹配的坑） | 用假的 `env` + 假 db 调用 `handleRequest()`，断言：`/health` 返回 200、未知路径 404、`/api/movies/latest` 不被 `/:id` 吃掉、缺少 token 的写操作返回 401 |
| **P1** | **源探活的"离线可重复"用例** | 真实源会挂、会被限频，`LIVE` 用例天然不稳定；但"源被跳过 / 降级 / 冷启动不剔除"的逻辑必须锁死 | 已有部分（源健康 UNIT）。继续补：`down` 源不参与排序、`degraded` 后置、`allowProbe:false` 绝不发网络请求、过期缓存不得用于过滤 |
| **P2** | **前端组件级测试** | 前端目前**零测试**，`_headers`、XSS 清洗、路由守卫这些只能靠人眼 | 只为"安全 + 路由"两件事引入轻量测试（如 `node --test` + 直接调用纯函数 `sanitizeHtml`）；**不要**为 UI 细节建测试 |

### 2.3 哪些**不值得**测（明确写出来，避免浪费）

- ❌ **UI 像素 / 布局**：靠截图人眼验收，写测试的维护成本远超收益。
- ❌ **第三方源的返回内容**：源站天天变，测它等于测别人。只测**我们对它的处理**。
- ❌ **`LIVE` 类用例当成 CI 必过项**：源站限频会让它随机红。它应该是"手动跑 / 定时跑"的诊断工具，不是闸门。
- ❌ **为了覆盖率数字写测试**：覆盖率不是目标。**只测"改错了会很痛"的地方**（权限、数据写入、路径解析、安全清洗）。

### 2.4 一条硬规则：写测试前先问三个问题

1. 这段逻辑**改错会怎样**？（会漏数据 / 越权 / 崩 → 值得测）
2. 这个测试**会不会因为外部原因随机红**？（会 → 移出 CI 闸门）
3. 三个月后**还看得懂吗**？（看不懂的测试等于负债）

> 口诀：**"测逻辑，不测运气；测边界，不测像素。"**

## 3. 现在怎么部署（必须先搞清的事实）

| 工作流 | 触发 | 干什么 | 需要 Secret |
| --- | --- | --- | --- |
| `deploy-frontend.yml` | push `main` 且改 `frontend/**` | `npm ci` + `npm run build` + 发布到 Pages | Cloudflare + `VITE_*` 三个 |
| `deploy-backend.yml` | push `main` 且改 `backend/**` | `npm ci` + **先跑 test:unit** + 同步 Worker secrets + `wrangler deploy` | Cloudflare + Supabase 三个 |
| `db-migrate.yml` | push `main` 且改 `supabase/migrations/**` | `supabase link` + `supabase db push` | Supabase 三个 |
| `quality.yml` | 任何 push / PR | 前端构建 + 后端测试 + 凭据扫描（只读，不部署） | 无 |
| `secret-scan.yml` | 任何 push / PR | 扫描工作树**与全部提交历史** | 无 |

**关键点（也是风险点）**：

1. **推 `main` 就等于上线**——没有人工确认这一步。
2. 三个部署工作流**各自独立触发**。如果一次提交同时改了 `frontend/` + `backend/` + `migrations/`，
   三个工作流**并发跑**，谁先完成不确定 → **顺序风险**（见 §4.4）。
3. 部署工作流都有 **Secrets 非空预检**，缺 Secret 会**主动失败**（这是刻意设计：宁可不上线，也不上线一半）。
4. 前端构建时 `VITE_API_BASE_URL` 等变量在构建期就被**烧进产物**，所以换环境必须重新构建。

## 4. CI/CD 改进建议

### 4.1 是否引入 PR + 预览环境？

**建议：引入，但只对"中大型改动"强制。** 理由：

- Cloudflare Pages 对**非 main 分支的 push** 会自动生成**预览地址**（`<hash>.<project>.pages.dev`），
  这是**免费**的，不需要额外配置。等于"白送一个线上预览"。
- 但**后端 Worker 没有"预览环境"**（除非再建一个 Worker，成本上升）。所以预览只能验前端。

**落地方式（低风险、渐进）**：

| 改动类型 | 做法 |
| --- | --- |
| 文案 / 单个样式 / 加一个源 | 直接 `main`，自动部署，够快 |
| 一个页面的重排、一个模块的半成品收尾 | 开分支 → 推分支拿到 Pages 预览 → 人眼确认 → 合并 `main` |
| 设计系统、新模块、权限模型、数据库结构 | 开分支 + PR（写清改了什么 / 怎么验 / 怎么退）→ 确认后合并 |

> 给站长的话：**"分支 = 草稿本"**。在草稿本上改，网站线上**一点变化都没有**；
> 确认满意了再"合并"，那一刻才上线。草稿本推上去还能自动生成一个**临时网址**给你先看。

### 4.2 部署回滚方案（现在没有，必须补）

| 层 | 回滚方式 | 前提 |
| --- | --- | --- |
| 前端（Pages） | Cloudflare 控制台 → Pages 项目 → Deployments → 选历史版本 → **Rollback** | 每次部署都留版本，天然可回滚 |
| 后端（Worker） | `npx wrangler rollback`（回上一个版本），或控制台选历史版本 | wrangler 会保留版本历史 |
| 代码 | `git revert <commit>` 后推 `main`（**不要** `reset --hard` 强推） | 提交历史干净 |
| 数据库 | **不能"回滚"**，只能**前滚**：再写一个迁移把状态改回去 | 见 §4.4 的迁移纪律 |

**建议做法**：

1. 把上面这张表写进 `docs/deployment.md`（现在只有一句"已记录回滚方式"，没有步骤）。
2. **演练一次**：随便发一个无害改动，然后用上面的方式回滚，确认真的可行。
   没演练过的回滚流程 = 没有回滚流程。
3. 部署后固定做**两件事**：`/health` 是否 200；关键页面是否 200。

### 4.3 数据库迁移与代码部署的**顺序风险**（重要）

这是最容易"上线一半坏掉"的地方。三种情况：

| 情况 | 风险 | 正确顺序 |
| --- | --- | --- |
| 只加表 / 加列（可空） | 低 | 先迁移，后部署代码（旧代码不认识新列也不报错） |
| 改列语义 / 加非空约束 / 删列 | **高**：旧代码可能正在用被删的列 | **三步走**：① 先部署"兼容两种结构"的代码 → ② 再跑迁移 → ③ 最后再部署"只用新结构"的代码并清理 |
| 只改代码，不改库 | 低 | 随便 |

**硬规则**：**永远不要在一个提交里"既删列又改代码"**。
必须让"旧代码 + 新库"和"新代码 + 旧库"这两个中间态**都能跑**。

> 现实提醒：`db-migrate.yml` 一直因缺 `SUPABASE_ACCESS_TOKEN` / `SUPABASE_DB_PASSWORD`
> 而**失败**（迁移是人工手动跑的）。补上这两个 GitHub Secret 之前，**不要假设迁移会自动应用**——
> 每次改库都要在汇报里明确写"迁移已手动应用 / 未应用"。补 Secret 的步骤见 `docs/handoff-r2-assets.md` 第 3 节。

### 4.4 Secrets 管理规范（照抄即可）

| 规则 | 说明 |
| --- | --- |
| **值只存一处** | 生产值只放在 GitHub Secrets 与 `wrangler secret`；本地只放 `backend/.dev.vars` / `supabase/.env.local`（均已在 `.gitignore`） |
| **文档只写变量名** | 文档里永远写 `$SUPABASE_DB_PASSWORD`，**绝不写值**。这是 2026-10-08 事故的直接教训 |
| **提交前必扫** | `.githooks/pre-commit` + `scripts/check-secrets.mjs`；CI 里 `secret-scan.yml` 再扫一遍全历史 |
| **轮换优先于清理** | 一旦泄漏，**先轮换凭据（止血）→ 再脱敏 → 最后重写历史**，顺序不能反 |
| **空值不得覆盖** | 部署时"仓库 Secret 为空则跳过 `wrangler secret put`"，否则会把线上密钥覆盖成空串 |
| **新增 Secret 必须登记** | 在 `docs/deployment.md` 的清单里加一行，写明"用途 + 谁去配 + 不配会怎样" |

## 5. 可观测性（现在几乎为零，这是最大的工程缺口）

### 5.1 现状

- Worker 打开了 `[observability] enabled = true`（`backend/wrangler.toml`），但**没有人看**。
- 没有错误上报（Sentry 之类），没有可用性监控，源失败**不会主动通知任何人**。
- 站长通常靠"自己打开网站发现不对"才知道出事了。

### 5.2 免费方案（按性价比排序，全部在免费额度内）

| 优先级 | 做什么 | 免费方案 | 效果 |
| --- | --- | --- | --- |
| **P0** | **可用性监控（外部探活）** | Cloudflare 自带的 Health Checks（部分套餐）；或免费第三方监控（如 UptimeRobot / BetterStack 免费档）定时探 `https://api.xuguochen.de5.net/health` 与前端首页 | 站点挂了 5 分钟内收到邮件 / 推送 |
| **P0** | **源失败告警（应用内）** | 复用已有的**通知中心**（`notifications` 表 + `POST /api/notifications`）：定时任务发现某源连续 N 次 `down` 时写一条通知 | 打开网站就能看到"某源挂了"，不用翻日志 |
| **P1** | **错误上报** | Sentry 免费档（Workers 支持），只上报 `5xx` 与未捕获异常 | 有堆栈、有上下文，不用靠猜 |
| **P1** | **关键指标日志** | `wrangler tail` + 结构化 `console.log`（已有 `[cron]`、`github ai` 日志的习惯，继续沿用） | 排查"什么时候开始坏的" |
| **P2** | **前端真实用户错误** | 轻量自建：`window.onerror` + `unhandledrejection` 上报到后端一个只写接口 | 知道用户端白屏了 |

### 5.3 具体建议：先做"最小可用三件套"

1. **探活**：每分钟探 `/health`，连续 2 次失败发通知（或邮件）。
2. **源告警**：`sourceHealth` 的结果里，若某源 `status=down` 且**连续 3 次探测**都 down，
   往 `notifications` 写一条 `system` 类型通知（站长登录可见）。
3. **错误可见**：Worker 里所有 `catch` 分支统一 `console.error('...', err.stack)`（现状大多如此，保持），
   并把 `[observability]` 打开后**真的定期看一眼**（站长可以让 Agent 每周汇总一次）。

> 提醒：**不要**为了可观测性引入需要付费 / 需要自建服务器的方案（如自建 Grafana）。
> 这个项目的规模用"探活 + 通知中心 + 免费错误上报"就够。

## 6. 数据与迁移规范

### 6.1 迁移文件：只增不改（铁律）

- 唯一改表入口是 `supabase/migrations/*.sql`，**禁止**在网页后台手动改表（应急除外，且必须立刻补迁移）。
- **已执行过的迁移文件不得修改内容**——改它对线上没有任何效果，只会让"本地 / 线上"不一致。
- 每次改库**新建一个带时间戳的迁移文件**，例如 `20261010000016_gallery_items.sql`。
- 迁移里写清**注释**：这次为什么改、影响什么、有没有数据回填。
- 命名风格沿用现状：`YYYYMMDD0000NN_描述.sql`（现有最大编号见 `supabase/migrations/`）。

### 6.2 RLS 与 `service_role` 的关系（最容易误解的一点）

```
真实浏览器用户 → Supabase Auth 签发的 JWT → （前端直连 Supabase 时）RLS 生效
Worker（后端）  → service_role key 直连 PostgREST → RLS **不生效**
```

**结论**：

- RLS 策略是**第二道防线**（防止有人拿 anon key 直连数据库乱来），**不是** Worker 的权限控制。
- Worker 的权限控制**完全靠自己写的过滤条件**：`user_id=eq.${user.id}` + 公开过滤。
- 因此：**改任何读路由，都必须检查它有没有叠加 `publicScope.js` 的过滤**。

### 6.3 写操作铁律：必须带 `user_id`

- 任何 **insert / update / delete / 进度写入**，都必须显式带 `user_id = 当前用户 id`。
- **管理员也不能写别人的数据**：管理员的特权只有 `?all=true` 的**读**。
- 例外（需明确注释说明）：`assets` 上传（仅站长）、`notifications` 系统通知、备份导入（仍按当前用户写）。
- 关联表（`post_tags` / `resource_tags` / `resource_links`）的删除也要带 `user_id`，
  否则会删到别人的关联（这是已修复过的真实缺陷）。

### 6.4 备份与恢复演练

| 项 | 现状 | 建议 |
| --- | --- | --- |
| 应用层备份 | 已有 `/api/backup/export` 与 `/api/backup/import`（v2，覆盖主要表） | 保持；**导入是逐条写入、非事务**，大批量导入失败会部分写入 → 导入前先导出一份当前状态 |
| 数据库备份 | Supabase 免费档有每日备份（保留期有限） | 每周手动导出一次关键表（或让 Agent 导出），存到本地 / R2 之外的独立位置 |
| 恢复演练 | **从未做过** | 至少演练一次：导出 → 清空测试数据 → 导入 → 核对条数。没演练过的备份等于没有备份 |
| 二进制（R2） | 只存元数据，图片在 R2 | R2 数据不随数据库备份走；重要图片要单独留存 |

## 7. 多 Agent 协作规范（结合 `~/AGENTS.md` 第 10、11 节）

### 7.1 唯一总纲：零共享写入

> **任何文件，同一时间只能有一个 Agent 写。** 不存在"两个 Agent 一起编辑同一个文件"。

落到这个仓库，具体是：

| 场景 | 规则 |
| --- | --- |
| 两个 Agent 改不同模块 | **各自开分支**（或各自独立工作目录），互不写入对方的文件 |
| 两个 Agent 都要改同一个文件（如 `global.css`、`router.js`、`api.js`） | **禁止并行**。串行做，或由一人先做完、另一人再基于新版本改 |
| 共享资源（`docs/progress.md`、`README.md`、`wrangler.toml`、`package.json`） | **单一所有者**，其他人只读；要改先问站长 |
| 需要"全局视图"时 | **聚合读取**（主 Agent 读各分支 / 各进度文档汇总），**不要**让所有人写同一张表 |

### 7.2 `OWNERS.md` 要不要建？

**建议：要建，但保持极简。** 现状是"多 Agent 并行改同一仓库，没有文件归属"，
这正是 `~/AGENTS.md` 第 11.3 节要求 `OWNERS.md` 的场景。

建议内容（放在仓库根，一屏以内）：

```markdown
# 归属声明（OWNERS）

## 共享资源（只读，除所有者）
- 所有者：站长指定
- 共享文件：README.md、docs/progress.md、backend/wrangler.toml、
            frontend/src/styles/global.css、backend/src/router.js、frontend/src/lib/api.js
- 规则：仅所有者可修改；其他 Agent 只读，需要改先问站长。

## 任务归属
| 目录 / 模块 | 负责人 | 状态 | 分支 |
| --- | --- | --- | --- |
| （每次派活时登记一行） | | | |
```

> **注意**：`OWNERS.md` 本身是"会被多人写"的文件 → 它必须有**唯一所有者**（建议站长或调度 Agent），
> 其他 Agent 只读。不要制造新的共享写入点（这是 `~/AGENTS.md` 第 10.4.1 节的教训）。

### 7.3 分支策略（给站长讲清楚"分支是什么"）

**用最直白的话**：

- **`main` = 正式版**。往它推代码，GitHub Actions 自动部署，几分钟后网站就是新的。
- **分支 = 草稿本**。在草稿本上改，**线上一点变化都没有**；改完确认没问题，再"合并"进 `main`。
- **合并那一刻才上线**。合并前，草稿本可以随便改、随便推，还能自动生成一个**临时预览网址**。

**推荐策略（明确给结论）**：

| 改动类型 | 建议做法 | 理由 |
| --- | --- | --- |
| 小改：文案、单个样式、加 / 换一个源、修一个 bug | **直接在 `main` 上做** | 快，自动部署，回滚也容易（`wrangler rollback` / Pages Rollback） |
| 中改：一个页面的重排、一个半成品的收尾 | **开分支 → 预览确认 → 合并** | 避免"改到一半线上是坏的" |
| 大改：设计系统、新模块、权限模型、数据库结构 | **开分支 + PR 预览 + 明确验收清单 → 合并** | 影响面大，必须能先看、能回退 |

**分支命名约定（沿用现有习惯）**：`feat/<模块>`、`fix/<模块>`、`docs/<主题>`。

> 站长只需要说一句："**这个是中改，开个分支先给我看。**" Agent 就该照 §7.3 执行。

### 7.4 文件归属：哪些文件"天生冲突"，必须串行

| 文件 | 为什么危险 | 处理 |
| --- | --- | --- |
| `frontend/src/styles/global.css` | 所有页面样式都在这一个文件里，两个 Agent 同时改必然冲突 | **一次只允许一个 Agent 改**；新样式尽量写进独立 css 文件再引入 |
| `backend/src/router.js` | 路由表是所有模块的"总开关" | 加路由时**只追加**，不要重排；同一时间一人改 |
| `frontend/src/lib/api.js` | 前端所有接口调用的唯一出口 | 同上；CONTRACT 测试会强制"前后端同步" |
| `docs/progress.md` | 唯一的接力文档 | **单一所有者**；其他 Agent 只读，靠汇报让所有者更新 |
| `backend/wrangler.toml` | 绑定 / Cron / 变量都在这里 | 单人改；改完必须说明影响（Cron 会真的跑） |

### 7.5 交接文档怎么写、`docs/progress.md` 的维护节奏

`docs/progress.md` 是这个项目的**长期记忆**（对话上下文会丢，它不会）。要求：

| 时机 | 必须更新哪几节 |
| --- | --- |
| 每完成一轮开发 | 「当前状态」「本轮完成内容」「下一步」 |
| 遇到失败 / 返工 / 踩坑 | **立刻**记入「坑与注意」（不要事后回忆） |
| 有需要站长决策的事 | 记入「下一步 / 待决策」，并在对话里同步提醒 |
| 换 Agent 前 | 确保最新一轮已完成内容 + 下一步 + 坑都是最新 |

**一份合格的交接，必须能让"完全没参与过的 Agent"在不问你任何问题的情况下开工。**
自检问题：*新 Agent 读完 `progress.md`，知道①现在到哪了 ②下一步做什么 ③哪些坑不能踩 ④怎么验证吗？*
