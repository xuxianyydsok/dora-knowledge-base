## 0. 先看结论（站长 30 秒版）

1. **定位升级**：从"知识库 / 博客站"升级为 **Dora Studio · 个人数字资产中心**。
2. **近期只做 4 件事**：公开/私密控制入口、音乐与影视页收尾、画廊 + 时间线（已在做）、源健康增强。
3. **强烈推荐做**：画廊、时间线（已有分支在开发）。
4. **观望**：读书笔记、简历作品集、域名邮箱、留言墙。
5. **不建议做**：多用户社区、评论系统、在线编辑器大改、自建后端服务、付费 CDN。
6. **成本**：现在所有服务都在**免费额度内**。最烧额度的是
   **Workers AI 解读**、**R2 存储 + 图片流量**、**Supabase 数据库体积**——省钱建议见 §5。

## 1. 重新定位：从"知识库"到"个人数字资产中心"

### 1.1 旧定位的问题

项目最初叫"知识库"，后来改名 Dora。但它现在的实际能力**早就超出"博客"了**：

| 已有能力 | 按"博客站"看 | 按"个人数字资产中心"看 |
| --- | --- | --- |
| 315 篇博客 + 分类 / 标签 / 归档 / 检索 | 主功能 | 内容资产的一种 |
| GitHub Star 同步 + AI 中文解读 | 看不懂的东西 | **你的技术兴趣图谱**（1,300+ 条已被 AI 分类） |
| 音乐库 + 多源聚合 + 无损 + 歌词 | 花边功能 | **你的音乐资产**（可收藏、可播放、有进度） |
| 影视库 + 7 个采集源 + 播放代理 | 花边功能 | **你的观影资产**（片单、进度、重匹配） |
| 知识图谱控制台 | 玩具 | **全站资产的关联视图**（博客 ↔ 标签 ↔ 资源） |
| 图片素材（R2）+ 备份导入导出 | 附属 | **真正的资产存储与迁移能力** |
| 管理员 MCP | 内部工具 | **AI 可以写入你资产库的入口** |

**结论**：这不是"一个博客"，这是**一个属于你一个人的、可被 AI 操作的数字资产中心**。

### 1.2 一句话价值主张

> **Dora Studio —— 把你散落在各处的数字资产（文章、代码收藏、音乐、影视、图片）
> 收进一个你能掌控、AI 能帮你打理的地方。**

拆开看三层：

| 层 | 说给谁听 | 一句话 |
| --- | --- | --- |
| **对内（你自己）** | 站长的自我定位 | "我的东西，都在一个地方，我说了算。" |
| **对外（访客）** | 展示给别人的形象 | "这是我的数字作品集与技术品味。" |
| **对 AI（Agent）** | 可被操作的能力 | "Agent 可以通过 MCP 帮我写文章、加收藏、整理标签。" |

### 1.3 关于改名 "Dora Studio"

| 项 | 建议 |
| --- | --- |
| 是否改名 | **建议改，但不急**。改名的成本主要在"记忆"和"链接"，不在代码 |
| 什么时候改 | **等近期 4 件事做完之后**（现在改名会打乱正在开发的分支） |
| 要改哪些地方 | 前端站点标题 / Logo 文案、`README.md`、`docs/*` 说明、Supabase 项目显示名、Cloudflare 项目显示名 |
| 不改什么 | **不要改**域名（改了所有外链失效）、**不要改**仓库名（改了 CI / Secrets 要重配） |
| 折中做法 | 先只改**页面上的展示名**为 "Dora Studio"，域名与仓库保持不动 |

> 站长视角：**改名只改"牌子"，不动"地基"**。地基一动（域名、仓库名），所有自动化都要重配，不划算。

### 2.2 候选新模块（逐个评估）

评估口径：**解决什么问题 / 成本 / 依赖 / 是否推荐**。

---

#### ① 画廊 `/gallery`（图片展览）

- **解决什么问题**：现在图片素材只服务于"博客封面 / 插图"。你自己的照片、截图、作品图
  没有地方**成体系地展示**。画廊 = "策展"，素材库 = "仓库"。
- **成本**：中（1 个新表 + 3~4 条接口 + 1 个页面 + 1 个管理页）。
- **依赖**：R2 图片素材系统（已上线 ✅）、`assets` 表（已上线 ✅）。
- **是否推荐**：✅ **强烈推荐**——**已经在 `feat/gallery-timeline` 分支开发中**，
  有独立任务书 `~/tmp/briefs/gallery-timeline-brief.md`。
- **注意**：画廊与"图床"不同。图床是"存图给别处用"，画廊是"展示图"。
  两者共用 `assets` 表，但**画廊需要额外的策展元数据**（标题、说明、拍摄日期、排序、是否公开）。

#### ② 时间线 `/timeline`

- **解决什么问题**：把"什么时候做了什么"串成一条线（发布了什么文章、收藏了什么、
  听了什么、看了什么）。是**个人数字资产的编年史**。
- **成本**：中（复用 `posts` / `resources` 的时间字段，主要是查询 + 聚合 + 一个页面）。
- **依赖**：`posts` / `resources` 的 `created_at`（已有 ✅）；**注意** `resources` 线上 `is_public` 全为 `false`，
  访客视角的时间线暂时只有博客部分（预期行为）。
- **是否推荐**：✅ **推荐**——与画廊**同批开发**（`feat/gallery-timeline` 分支），共用一套时间聚合逻辑。

#### ③ 留言墙

- **解决什么问题**：让访客留个话 / 说声"来过"。目前站点是**纯只读展示**，没有任何互动。
- **成本**：中高。表面是"一个页面 + 一张表"，实际是**一整套运营负担**：
  垃圾信息过滤、内容审核、举报、频率限制、违规内容责任。
- **依赖**：需要开放**写权限给匿名访客**——这与当前"访客只读 + 写操作必须登录"的安全模型**直接冲突**。
- **是否推荐**：⚠️ **观望，暂不建议做**。
  理由：① 你的定位是"个人资产中心"，不是社区；② 一旦开放匿名写入，
  当前的权限模型要重做，风险远大于收益；③ 如果只是"想看谁来过"，用访问统计更省事。
  **如果哪天要做**，必须**先做**：人机验证 + 频率限制 + 先审后发 + 只对登录用户开放。

#### ④ 域名邮箱

- **解决什么问题**：有个 `你@你的域名` 的邮箱，看起来专业，也能收站点通知。
- **成本**：**中（技术）+ 低（钱）**，但**有坑**：
  - 收信：Cloudflare Email Routing **免费**，把 `xx@你的域名` 转发到你的真实邮箱（5 分钟配好）。
  - 发信：**不免费**（Cloudflare 只做转发，不做发信）。发信要走第三方（需付费或有限免费额度）。
- **依赖**：域名已托管在 Cloudflare（✅ 已满足）。
- **是否推荐**：✅ **推荐先做"收信转发"**（免费、无风险、10 分钟搞定）；
  ⚠️ **发信观望**（要付费 / 要接第三方，且你自己已有邮箱，收益不高）。
- **隐私提醒**：域名邮箱会**暴露你的域名**，也可能被爬虫收集。
  建议**只给管理员用**（收站点告警、收通知），**不要**开放给访客注册用（见 `04` 文档的注册系统取舍）。

#### ⑤ 读书笔记

- **解决什么问题**：博客之外的"碎片化阅读产出"——一本书的摘抄、想法、进度。
- **成本**：中。**可以低成本实现**：不建新表，直接用 `posts` 的**一个分类 + 一个标签**
  （如分类"读书笔记"），加一个"在读 / 读完"的自定义字段（用标签实现）。
- **依赖**：无新依赖（复用博客系统）。
- **是否推荐**：⚠️ **观望，但可以先"零成本试水"**。
  先用博客分类 + 标签写几篇，**确认自己真的会持续写**，再考虑做专门的页面（书籍封面墙、进度条）。
  > 教训：**先验证"会不会用"，再投入"开发成本"**。这是本项目最重要的一条产品纪律。

#### ⑥ 简历 / 作品集页

- **解决什么问题**：对外展示"我是谁、我做过什么"——把博客 + GitHub + 画廊挑出一部分，
  拼成一个**对外门面**。
- **成本**：低~中。**可以完全复用现有数据**（博客精选 + GitHub Star + 画廊），
  本质是一个"精选聚合页"。
- **依赖**：画廊（若要展示图片作品）。**不依赖**任何新服务。
- **是否推荐**：✅ **推荐（排在画廊之后）**。
  这是"个人数字资产中心"**对外价值最直接**的一个页面，而且**成本低、无风险**（纯只读展示）。
  建议做成 `/about` 或 `/portfolio`，站长可挑选展示哪些内容。

#### ⑦ MCP 对外接口（开放给其他 Agent）

- **解决什么问题**：让**别的 AI Agent**（不只是你自己在网页上操作）能帮你写文章、加收藏、整理标签。
- **成本**：技术成本中，**风险成本高**（见 §4 详解）。
- **依赖**：现有管理员 MCP（`/api/mcp/*`，已上线 ✅）。
- **是否推荐**：⚠️ **观望，按 §4 的方案分阶段开放**。
  **绝不建议**直接把现有管理员 MCP 暴露给外部 Agent——它现在的能力是"以站长身份写库"。

## 3. 优先级路线图（三期）

> 排序原则：**先"让网站看起来完整"，再"让内容更丰富"，最后"才谈扩展"。**
> 每一期都给出"**为什么是现在**"。

### 第一期：收尾与完整（近期，约 1–2 周）

| # | 事项 | 为什么是现在 |
| --- | --- | --- |
| 1 | **公开 / 私密内容控制入口**（单项 + 批量） | 线上资源 `is_public` 全为 `false` → 访客看到的是**空站**。这是"网站能不能给人看"的前置条件 |
| 2 | **音乐页收尾**（音乐库入口回到页面 + 清理死代码） | 页面处于半成品，用户一眼能看出 |
| 3 | **影视库改海报墙**（搜索区 / 片库区分开） | 影视产品的第一眼观感 |
| 4 | **画廊 + 时间线**（`feat/gallery-timeline` 分支收尾） | 已经在开发，收尾成本最低；且它是"个人数字资产中心"定位的**第一个新证据** |
| 5 | **源健康面板增强 + 给普通用户只读版** | 源随时会挂，这是站长最初的核心诉求之一 |

**上线判据**：随便点开 5 个页面，页头结构一致；访客能看到**非空**内容。

### 第二期：可靠与体验（中期，约 1–2 周）

| # | 事项 | 为什么是现在 |
| --- | --- | --- |
| 6 | **源定期自动探活 + 失败自动降级 + 通知** | 第一期的面板只能"手动看"，第二期让它"主动告诉你" |
| 7 | **存量死链批量自愈**（复用已上线的 `refresh-source` 接口） | 接口已上线，只是缺一个批量入口，投入小、收益直接 |
| 8 | **播放体验**（记忆进度、选集、移动端手势） | 内容能播之后，"好不好用"才成为瓶颈 |
| 9 | **编辑页三胞胎抽公共骨架 + 图片上传** | 三个编辑页各写各的，改一次要改三处 |
| 10 | **设置页扩展为偏好中心** | 现在只有主题切换，"改密码 / 看账号"没地方去 |
| 11 | **分支策略 + 交接规范落地**（见 `05` §7） | 多个 Agent 并行改仓库已成常态，再不定规矩就要出事 |

**上线判据**：源挂掉能在面板看到并自动避让；播放能续播。

### 第三期：扩展与打磨（远期，持续）

| # | 事项 | 为什么是现在 |
| --- | --- | --- |
| 12 | **简历 / 作品集页** | 前面把内容做厚了，才值得"对外挑一份精选" |
| 13 | **域名邮箱收信 + 站点告警接入** | 需要先有告警源（第二期），否则邮箱没用 |
| 14 | **测试补齐 + 可观测性**（见 `05` §2、§5） | 项目越大越需要安全网；此时投入回报最高 |
| 15 | **MCP 对外接口的安全开放**（按 §4 方案分阶段） | 前面的权限 / 审计 / 备份都齐了，才敢对外开门 |
| 16 | **Dora Studio 改名落地** | 所有近期改动稳定后，再动"牌子"，避免打乱开发 |

**上线判据**：访客能通过简历页了解你；站点异常你能主动收到通知。

### 路线图一句话总结

```
第一期：把"半成品"变成"完整品"（好看、不空）
第二期：把"能用"变成"可靠、顺手"（不挂、不烦）
第三期：把"自己的站"变成"能对外、能开放"（可展示、可被 AI 操作）
```

## 4. MCP 接口对外：能力边界、风险与安全开放方案

### 4.1 现有 MCP 能做什么（能力边界）

`/api/mcp/*` 是**管理员专用**端点，现有工具（`backend/src/routes/mcp.js`）：

| 工具 | 能力 | 危险等级 |
| --- | --- | --- |
| `create_post` | 创建博客（可含标签、关联资源） | 中（写内容） |
| `update_post` | 按 id / slug **更新**已有博客 | **高**（可覆盖已有内容） |
| `add_video` / `add_github_repo` / `add_music` / `add_movie` | 新增各类资源 | 中 |
| `link_resources` | 把资源绑定到博客（**覆盖式**） | 中高 |
| `list_resources` | 列出管理员本人资源 | 低（只读） |
| `list_assets` / `set_post_cover` / `upload_image` | 图片素材：列出 / 设封面 / base64 上传 | 中（`upload_image` 会写 R2，烧存储） |

**边界（现在的设计）**：

- 鉴权是**管理员 JWT**——即"以站长身份操作"。
- 写操作严格限定 `user_id = 当前用户`，**管理员也不能写别人的数据**。
- 没有"删除"类工具（刻意不给）。
- 没有 `list_posts` / `get_post` 之类的**读取**工具（AI 想改文章得先知道 id，现在只能靠站长给）。

### 4.2 开放给其他 Agent 的风险

| 风险 | 具体场景 | 后果 |
| --- | --- | --- |
| **权限过大** | 外部 Agent 拿到一个能 `update_post` 的令牌，等于拿到"站长账号" | 可以改 / 覆盖你的任何文章 |
| **无审计** | 现在没有任何"谁在什么时候调了什么工具、改了什么"的记录 | 出事查不出原因 |
| **误写 / 误删数据** | AI 幻觉：把 slug 猜错、把 `update_post` 当 `create_post` 用、把 `linked_resources` 覆盖成空 | 内容被静默改坏 |
| **额度消耗** | `upload_image` 写 R2；未来若加 `analyze` 类工具会烧 Workers AI | 免费额度被外部 Agent 用光 |
| **令牌泄漏** | 外部 Agent 的运行时（第三方平台）可能记录令牌 | 泄漏 = 站长身份泄漏 |
| **并发写** | 两个 Agent 同时 `update_post` 同一篇文章 | 后写覆盖先写（零共享写入原则被破坏） |

### 4.3 安全开放方案（分阶段，**明确推荐"先别开"**）

**总原则：MCP 的"读"和"写"必须分开授权；写操作必须可审计、可回滚、可限流。**

| 阶段 | 做什么 | 开放程度 |
| --- | --- | --- |
| **阶段 0（现状）** | 只有站长自己在受控环境下调用 | 不开放 ✅ 保持 |
| **阶段 1：只读令牌** | 新增一种**只读 MCP 令牌**，只能调 `list_*` / 未来加的 `get_*`；**不能**写任何东西 | 可开放给外部 Agent 做"了解你的资产" |
| **阶段 2：草稿令牌** | 写操作**只能创建草稿**（`status=draft`、`is_public=false`），**不能**发布、不能改已有内容 | 可开放给"帮你写初稿"的 Agent |
| **阶段 3：受限写令牌** | 允许改**自己创建**的内容（记录 `created_by`），禁止覆盖站长手工编辑过的内容 | 需先有审计与版本 |
| **阶段 4：全权** | 等于站长身份 | **建议永远不开放** |

**落地时必须同时具备的四个机制**：

1. **审计日志**：新建一张 `mcp_audit` 表（或复用 `notifications`），记录
   `时间 / 令牌标识 / 工具名 / 参数摘要 / 影响的资源 id / 结果`。
   **注意**：参数摘要要脱敏，**不得记录任何凭据**。
2. **令牌分级**：不同令牌不同权限（只读 / 草稿 / 受限写），**不共用**站长 JWT。
3. **限流**：按令牌限速（如每分钟 N 次），防止被外部 Agent 刷爆额度。
4. **可回滚**：所有写操作前自动留一份"改动前快照"（至少对 `posts`），
   或明确要求走"先草稿、站长确认后发布"的流程。

> **给站长的建议**：现阶段**不要开放**。等第一、二期做完、
> 有了审计日志与只读令牌，再考虑开放"只读 + 草稿"两级。
> 想省事的话，**永远只开放"只读"**——那已经能让外部 Agent 帮你做很多事了。

## 5. 成本与额度（省钱指南）

### 5.1 你现在用了哪些免费服务

| 服务 | 用途 | 免费额度（量级参考，**以官网当前说明为准**） |
| --- | --- | --- |
| Cloudflare Pages | 前端托管 | 请求不限量；每月构建次数有限（500 次量级） |
| Cloudflare Workers | 后端 API | 每天约 10 万次请求；单次 CPU 时间约 10 毫秒 |
| Cloudflare R2 | 图片素材 | 存储约 10 GB；读操作每月约 1000 万次；**流出流量免费** |
| Cloudflare Workers AI | GitHub 收藏中文解读 | 每天约 1 万 neurons（实测约 1,200 次解读） |
| Supabase（Free 档） | 数据库 + 登录 + RLS | 数据库约 500 MB；月流量约 5 GB；**长期无访问会被暂停** |
| GitHub Actions | CI / 自动部署 | 公开仓库免费；私有仓库有每月分钟数上限 |
| NewsNow（自建 Worker） | 新闻热榜 | 走 Cloudflare 免费额度 |

### 5.2 哪些操作**最烧额度**（按危险程度排序）

| 排名 | 操作 | 为什么烧 | 谁在触发 |
| --- | --- | --- | --- |
| 1 | **GitHub Star 同步**（每次全量分页）+ **AI 解读** | 1,300+ 仓库，每页 100 条要 14 页；每个 AI 解读约 8 neurons | 每天 Cron 自动跑 + 打开 GitHub 页时按需跑 |
| 2 | **图片上传与浏览**（R2） | 图片体积大、浏览次数多；**流量虽免费但操作次数计费** | 站长上传 + 访客浏览 |
| 3 | **影视 / 音乐搜索** | 一次搜索并发打 5~7 个外部源 + 元数据补全 | 每次用户搜索 |
| 4 | **影视播放代理**（`/api/vod/proxy`） | 每个 m3u8 分片都要过一次 Worker | 每次播放（分片很多） |
| 5 | **Supabase 查询** | 每次页面加载多个接口 | 所有访客 |
| 6 | **数据库体积** | 博客正文（HTML）+ GitHub metadata（含 AI 解读）体积大 | 长期积累 |

### 5.3 省钱建议（具体、可执行）

| # | 建议 | 效果 | 成本 |
| --- | --- | --- | --- |
| 1 | **AI 解读限流**：只在"打开 GitHub 页"时按需解读，**不要**加回每分钟 Cron | 直接省下最大的 AI 消耗 | 已这么做（`removed-features.md` 有记录，别加回来） |
| 2 | **Star 同步改增量**：只同步"最近变化"的仓库，而不是每天全量 14 页 | 省 Workers 请求 + GitHub 限速压力 | 需开发（中） |
| 3 | **图片先压缩再传**：上传前压到合理尺寸（如 2560 宽 WebP），别传 5–6 MB 原图 | 省 R2 存储 + 加载更快 | 零成本（养成习惯） |
| 4 | **列表页只取必要字段**：`/api/github` 已改成只返回列表字段（不要 `select=*` 拉全量 metadata） | 省 Supabase 流量 + Worker CPU | 已是现状，保持 |
| 5 | **源健康缓存 TTL 调大**：探活结果缓存时间越长，探测次数越少 | 省外部请求 | 改一个常量（低风险） |
| 6 | **影视 / 音乐搜索结果缓存**：热门关键词缓存几分钟 | 省源站请求 + 提速 | 需开发（中） |
| 7 | **定期清理无用数据**：过期的播放进度、失败的通知、不再引用的图片 | 省 Supabase 体积 + R2 存储 | 低 |
| 8 | **Supabase 别闲置**：免费档长期无访问会**暂停项目**，恢复要手动操作 | 避免"网站突然打不开" | 保持有访问即可（或定期登录后台） |
| 9 | **GitHub Actions 注意私有仓库分钟数**：不必要的重复 CI 会耗分钟 | 省钱 | 现状：`quality.yml` 只在 push/PR 跑，合理 |
| 10 | **R2 只存图片**：**不要**把音频 / 视频文件传进 R2（流量与存储会爆） | 避免大额账单 | 纪律（`docs/storage.md` 已写明） |

### 5.4 一条底线

> **任何可能"显著消耗额度"的新功能，Agent 必须先算一遍账再动手，并向站长说明。**
> 典型需要先算账的：批量抓取、定时全量同步、AI 批量处理、大文件上传、视频转码。

## 6. 不建议做的事（明确写出，避免浪费）

> 这一节和"推荐做什么"同样重要。**对个人站点来说，"不加"往往比"加"更有价值。**

| # | 看起来酷，但不建议 | 为什么 |
| --- | --- | --- |
| 1 | **做多用户社区 / 开放注册** | 一旦开放注册，就要做：用户管理、内容审核、滥用防护、隐私合规、客服。**这是"从个人站变成平台"，不是升级，是换赛道** |
| 2 | **做评论系统** | 同上 + 垃圾信息治理。且你的站是"展示型"，不是"讨论型" |
| 3 | **匿名留言墙** | 与当前"访客只读"安全模型直接冲突，等于给自己开后门 |
| 4 | **引入重型前端框架 / 全量重构** | 会推翻现有"液态玻璃"设计语言；重写 27 个页面的收益为负 |
| 5 | **自建服务器 / 自建数据库 / 自建 CI** | 免费额度完全够用；自建 = 自己承担运维、备份、安全。**个人站最大的成本是"维护精力"** |
| 6 | **付费 CDN / 付费图床** | R2 流出流量免费、Pages 请求不限量，没有付费的必要 |
| 7 | **把音视频文件存进 R2 / 数据库** | 存储与流量会迅速失控；影音走"外部源 + 代理"的现成模式 |
| 8 | **为了 SEO 做复杂的功能（SSR / 预渲染大改）** | 当前是 SPA，SEO 天生弱；改造成本极高。**先靠"内容质量 + 站点地图"就够**（详见 `04` 的 SEO 部分） |
| 9 | **加回 RSS 模块** | 用户已主动删除（`removed-features.md`）。**不要**因为"技术上很简单"就加回来 |
| 10 | **加回视频页** | 同上，用户已移除入口 |
| 11 | **把"30 秒试听"标成"无损 / 高音质"** | 虚假宣传，且违反项目已定的"如实标注"原则 |
| 12 | **在没实测的源上写"可用"** | 源必须实测（搜索 → 详情 → 分片）才能收录，这是项目的既有纪律 |

### 6.1 判断"该不该加一个新功能"的四问

1. **我自己会持续用吗？**（不是"听起来不错"）
2. **它会让维护变重吗？**（多一个要盯的服务 / 一张要备份的表）
3. **它和"个人数字资产中心"的定位一致吗？**（还是把我拖向"社区平台"？）
4. **能不能先用现有模块低成本试水？**（如读书笔记先用博客分类）

> **四问里有两个"否"，就别做。**
> 本项目最贵的东西不是服务器，是**你（和 Agent）的维护精力**。
