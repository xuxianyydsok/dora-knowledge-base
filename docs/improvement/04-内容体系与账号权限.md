## 1. 公开 / 私密边界（P0）

### 1.1 现状回顾（为什么访客看到的是空站）

| 内容类型 | 公开条件 | 线上现状 | 访客看到 |
| --- | --- | --- | --- |
| 博客 | `status=published` + `is_public=true` | 315 篇全部满足 | ✅ 正常 |
| 影视 | `is_public=true` | 7 条**全部 false** | ❌ 空 |
| 音乐 | `is_public=true` | 3 条**全部 false** | ❌ 空 |
| GitHub | `is_public=true` | 439 条**全部 false** | ❌ 空 |
| 视频 | `is_public=true` | 1 条 false | ❌ 空（视频页已下线，影响有限） |

> 注意：**影视/音乐的「搜索后直接播放」不受 `is_public` 影响**——
> 访客搜片、点歌是直接走采集源检索（`POST /api/movies/search`、`POST /api/music/search`），
> 不入库。所以「访客能不能搜到片」和「影视库列表是不是空」是两件事。

### 1.2 建议的产品形态（哪些该公开、哪些该私密）

**一句话原则：默认私密，站长手动「挑出来」公开。**

| 内容 | 建议默认 | 建议是否公开 | 理由 |
| --- | --- | --- | --- |
| 博客文章 | 草稿 / 私密 | **公开**（发布时勾上） | 博客就是给人看的 |
| 影视收藏（`movie`） | 私密 | **公开**（站长看过的片单，本来就是分享物） | 空着的影视页最影响观感 |
| 音乐收藏（`music`） | 私密 | **公开**（歌单天然适合分享） | 同上 |
| GitHub Star（`github`） | 私密 | **公开**（439 条，是「技术品味」的展示） | 这是最有价值的公开内容 |
| 视频（`video`） | 私密 | 保持私密（页面已下线） | 无入口，公开也没意义 |
| 分类 / 标签 | 公开 | 保持现状（字段已收窄） | 见 1.5 的残余风险 |
| 收藏夹（favorites） | — | **永不公开** | 属个人数据，后端已 403 |
| 播放进度 | — | **永不公开** | 后端已保证访客拿到的 `progress` 恒为 `null` |

**默认值怎么定（重要）**

- **不要**把数据库/接口的默认值从 `false` 改成 `true`。
  `backend/src/routes/movies.js` / `music.js` / `github.js` 的 `is_public` 默认 `false`
  是**安全默认**（新增内容不会意外泄漏）。
- 公开应该由**站长在操作时显式选择**，而不是「新增就公开」。
- 若确实想「GitHub Star 同步后自动公开」（439 条手动改不现实），
  建议只对这一条**特殊处理**：在 `backend/src/lib/githubStars.js#toRow` 里
  把 `is_public` 从写死 `false` 改为**读一个环境变量**（如 `GITHUB_STARS_PUBLIC`），
  默认仍为 `false`。这样既方便批量公开，又不会默认泄漏。

### 1.3 批量控制入口的设计（P0，工作量 M）

**现状**：影视 / 音乐 / GitHub 的**编辑页根本没有公开开关**。
`frontend/src/routes/MovieEdit.jsx`、`MusicEdit.jsx`、`Github.jsx` 里
**搜不到 `is_public`**——只有 `frontend/src/routes/PostEdit.jsx` 有「公开」复选框。
也就是说：现在**站长想公开一条影视，前端没有地方点**（只能调接口或改数据库）。

> `docs/progress.md` 第 3 节写的「各编辑页已有该开关」与代码实际情况不符，
> **这是本轮要修的**。

**建议做三层入口（从易到难）**

1. **单项开关**（P0，S）：在 `MovieEdit.jsx` / `MusicEdit.jsx` 加「公开」复选框
   （照抄 `PostEdit.jsx` 第 184 行的写法），保存时带上 `is_public`。
   GitHub 页没有编辑页，见第 2 条。
2. **列表页多选 + 批量**（P0，M）：
   - 后端加 `PATCH /api/{movies,music,github}/batch`（`requireAdmin` 或本人），
     body `{ ids: [...], is_public: true|false }`，**写操作严格 `user_id=eq.${user.id}`**；
   - 前端在 `frontend/src/routes/Movies.jsx`、`Music.jsx`、`Github.jsx` 加多选 + 顶部
     「批量公开 / 批量设为私密」按钮；GitHub 页现在**不渲染资源卡片**
     （只显示同步来的列表），多选实现要基于它现有的紧凑列表结构。
   - ⚠️ 批量接口必须**限制单次条数**（建议 ≤200），避免一次请求改太多。
3. **筛选 + 公开预览**（P1，S）：
   - 加「只看私密 / 只看公开」筛选（前端过滤即可，`is_public` 字段列表接口已返回）；
   - 加一个「以访客视角预览」按钮：调用同一接口时**不带登录态**看返回结果，
     或直接在新窗口打开 `/movies`（无痕模式）确认。

**涉及文件**

| 动作 | 文件 |
| --- | --- |
| 编辑页公开开关 | `frontend/src/routes/MovieEdit.jsx`、`frontend/src/routes/MusicEdit.jsx` |
| 批量接口 | `backend/src/routes/movies.js`、`backend/src/routes/music.js`、`backend/src/routes/github.js`、`backend/src/router.js` |
| 批量 UI + 筛选 | `frontend/src/routes/Movies.jsx`、`frontend/src/routes/Music.jsx`、`frontend/src/routes/Github.jsx` |
| 前端接口封装 | `frontend/src/lib/api.js` |
| GitHub 同步默认公开 | `backend/src/lib/githubStars.js` |
| 文档同步 | `docs/public-access.md`、`docs/progress.md` |

### 1.4 上线判据（怎么算做完了）

1. 用无痕窗口打开 `https://dora.xuguochen.de5.net/movies`，**能看到片单**（不是空页）；
2. `/music`、`/github` 同理；
3. 私密内容用无痕访问**返回 404 / 空列表**（不是把私密内容也放出去）；
4. 博客仍正常。

### 1.5 已知残余风险（知情接受，别当 bug 修）

来自 `docs/public-access.md` 第 5 节：

- 访客能看到站长的**全部分类/标签名称**（即使某些只服务于私密内容）；
- 公开资源的 `metadata`（JSON）对访客可见（含 GitHub star 数、AI 解读等）；
- 后端 `auth.js` 有模块级 `ownerCache`（「最早 admin」缓存），站长换人后同实例内可能短暂沿用旧 id。

**优先级 P0**（`00-总览` 列为 P0 第 4 项：「公开/私密内容控制入口」）。

## 2. 注册登录系统该不该做（决策类，P1）

> 站长原话是「怕麻烦、怕维护」。所以这一节的结论要**先讲代价**。

### 2.1 三种方案对比

| 方案 | 谁能进 | 成本 | 风险 | 维护量 | 适合什么情况 |
| --- | --- | --- | --- | --- | --- |
| **A. 完全公开**（现状） | 任何人只读 | **≈0** | 低（但内容全公开） | **≈0** | 现在这样：个人站点、只给人看 |
| **B. 仅站长登录** | 访客只读 + 站长登录后可写 | 低 | 低 | 低（就是现在，已具备） | **推荐**：个人站点 + 一个主人 |
| **C. 开放注册** | 任何人可注册、各自有账号 | **中–高** | **高** | **高** | 只有当你要「让朋友也来用」时才考虑 |

### 2.2 方案 C 为什么代价高（把丑话说在前面）

**技术成本**

- 邮箱确认 / 找回密码要走邮件通道（见第 4 节），否则用户注册了收不到确认信；
- 需要防滥用：注册限流、验证码、防机器人（否则会被灌垃圾账号）；
- 每个新用户的数据隔离要重新验证一遍（RLS 已有，但 Worker 用 `service_role` **绕过 RLS**，
  每条查询都要显式带 `user_id`，见 `docs/public-access.md` 第 3 节）；
- 用户多了会撞免费额度：Supabase 免费版有**数据库容量、月活用户（MAU）、带宽**上限，
  Workers 免费版每天 10 万次请求、单次 CPU 10ms。

**运营成本（更麻烦的部分）**

- 要有人处理「我密码忘了」「我发的文章怎么被删了」「这个人发广告」；
- 内容审核、举报、封号策略都要有；
- 数据备份与隐私（别人的数据存在你这里，责任变了）。

**安全成本**

- 2026-10-08 已经因为「凭据写进仓库」出过一次事故（`docs/security-2026-10-08.md`）。
  用户越多，一旦泄漏影响越大。

### 2.3 明确推荐

> **推荐方案 B：维持「访客只读 + 仅站长登录」的现状，不开放注册。**

**理由**

1. 你的目标是「给别人看」，不是「让人来发内容」——方案 A/B 完全够用；
2. 项目已有一套完整的登录体系（Supabase Auth + `frontend/src/routes/Login.jsx`），
   站长自己用没问题；
3. 开放注册的收益（多几个用户）远小于代价（邮件通道、防滥用、客服、额度）；
4. 数据库里其实**已经有** `site_settings.allow_public_registration` 这个开关
   （`supabase/migrations/20261006000001_init.sql`），未来真想开，
   **不用改数据库结构**，只要接上开关 + 加防护即可。留着这个可能性就够了。

**如果将来一定要开（触发条件）**

只有当出现下面这种情况才建议动：

> 「有 3 个以上朋友明确要求『我想自己往这里存东西』，而且愿意接受『我可能随时关掉』。」

届时按这个顺序做（**不要一次做完**）：

1. 先只做**邀请制**（站长手动建账号，走 `backend/src/routes/admin.js` 或 Supabase 控制台邀请），
   成本几乎为零；
2. 观察 1–2 个月，确认真的有人用、没有滥用；
3. 再考虑开放注册（届时才需要邮件通道 + 验证码 + 限流）。

**涉及文件（若将来要做）**：`backend/src/routes/admin.js`（邀请/建号）、
`frontend/src/routes/Login.jsx`（注册入口）、`backend/src/middleware/auth.js`、
`supabase/migrations/`（若要加邀请表）。

**优先级 P1**（决策类：**先看这一节再决定要不要派活**）。

## 3. 后台管理系统该不该做（决策类，P1）

### 3.1 两条路对比

| 对比项 | 「无后台 + MCP/脚本」（现状） | 「做一套后台」 |
| --- | --- | --- |
| 建设成本 | ≈0（已经能用） | **L**（新页面 + 新接口 + 新权限，至少 1–2 周） |
| 日常使用 | 站长在对话里让 AI 干（MCP 工具）或点页面上的编辑按钮 | 站长自己点后台表单 |
| 能力上限 | 受现有页面 + MCP 工具限制 | 想加什么加什么 |
| 维护成本 | 低（复用现有组件与接口） | **高**（每个模块都要维护一份后台 UI） |
| 风险 | 低 | 中（后台通常是权限漏洞高发区，本项目已修过一次越权） |

### 3.2 现状盘点：其实已经有一半「后台」了

- **管理员专用 MCP 端点**：`backend/src/routes/mcp.js`，
  工具包括 `create_post` / `update_post` / `add_video` / `add_github_repo` / `add_music` /
  `add_movie` / `link_resources` / `list_resources` / `list_assets` / `set_post_cover` / `upload_image`。
  **这就是「用对话当后台」**。
- **已有的管理页面**：`frontend/src/routes/AdminUsers.jsx`（用户管理：启用/禁用、改角色）、
  `frontend/src/routes/SourceHealth.jsx`（源状态）、`frontend/src/routes/Backup.jsx`（备份）、
  `frontend/src/routes/Settings.jsx`（设置）。

### 3.3 明确推荐

> **推荐：不做通用后台；只做「缺的那几块」的轻量页面。**

按「缺什么补什么」补，而不是先搭一个后台框架：

| 缺的功能 | 建议做法 | 优先级 |
| --- | --- | --- |
| 批量公开/私密（影视/音乐/GitHub） | 就在**现有列表页**加多选按钮（第 1.3 节） | P0 |
| 站点设置（如 GitHub Star 是否自动公开） | 在 `frontend/src/routes/Settings.jsx` 加一个开关，写 `site_settings` 表（**已有该表**，见 `docs/schema.md`） | P1 |
| 用户管理 | 已有 `AdminUsers.jsx`，够用 | — |
| 内容审核 / 评论管理 | **不做**（没开放注册就不需要） | — |
| 数据总览（多少篇博客、多少资源） | 可选：在 `Settings.jsx` 或新页加几个统计数字（复用 `GET /api/admin/users` 已有的统计口径） | P2 |

**为什么不推荐做后台**：站长要的是「少维护」。
每做一个后台页面，就多一份要跟着数据模型一起改的 UI；
而 **MCP + 现有编辑页已经覆盖了绝大多数操作**，成本低得多。

**涉及文件**：`frontend/src/routes/Settings.jsx`、`frontend/src/routes/AdminUsers.jsx`、
`backend/src/routes/mcp.js`（如需新工具）、`backend/src/routes/admin.js`。

**优先级 P1**（决策类）。

## 4. 域名邮箱集成（决策类，P1）

### 4.1 先分清两件事

| 用途 | 说明 | 与注册系统的关系 |
| --- | --- | --- |
| **收信**（如 `hello@你的域名`） | 别人给你发信、你有个「正式」的邮箱地址 | **无关**，纯品牌用途 |
| **发信**（系统发确认信/通知） | 注册确认、找回密码、播放链接失效提醒 | **强相关**：开放注册就必须要它 |

> **现在的状态**：项目**没有**任何发信能力。`docs/deployment.md` 里只写了一句
> 「若使用邮件确认/找回密码，确认 SMTP 与邮件模板已配置」——那是 Supabase Auth 侧的，
> 目前**未配置**。所以现在**不能开放注册**（用户收不到确认信）。

### 4.2 前提条件（要做才需要的）

1. 域名已托管在 Cloudflare（本项目已满足，见 `docs/deployment.md`）；
2. 在域名 DNS 里加 **MX / SPF / DKIM / DMARC** 记录（发信方会给你）；
3. 选一个发信服务（Cloudflare 生态里常用的是第三方，如 Resend、MailChannels 等；
   注意免费额度与「必须验证域名」的要求）；
4. 在 Supabase Auth 里配置自定义 SMTP（否则用的是 Supabase 默认发信，
   **有严格限流，且发信人不是你的域名**）。

### 4.3 隐私顾虑（站长原话：「不是每人想用多少就用多少」）

这句话的实质是**怕被人白嫖**。三个具体建议：

1. **分阶段：先只给站长自己用**
   - 阶段一：只配「收信」（`hello@` 之类），零风险，纯品牌；
   - 阶段二：只配「给站长自己发通知」（如源挂掉、备份提醒）——**收件人只有你自己**，
     没有任何隐私或滥用风险；
   - 阶段三：**只有当开放注册后才考虑**给用户发信。
2. **不要做「免费邮箱服务」**：不要让访客用你的域名收发邮件，
   那会立刻把域名送进垃圾邮件黑名单。
3. **不做「给用户发信」就不需要收集任何人的邮箱**——
   现在数据库里只有站长自己的账号邮箱（存在 Supabase Auth 里，**不入仓库**）。

### 4.4 明确推荐

> **推荐：只做阶段一 + 阶段二（收信 + 给站长自己发系统通知），不做面向用户的邮件。**

**具体落地（若要做）**

- 收信：Cloudflare 控制台 → Email → Email Routing，把 `hello@你的域名` 转发到站长已有邮箱。
  **不需要改代码**。
- 发系统通知：项目已有通知中心（`backend/src/routes/notifications.js`，表 `notifications`）。

## 5. 图床 / R2 素材（P1）

> 现状以 `docs/storage.md` 为准（该文档已在 2026-10-10 按实现重写）。

### 5.1 现有能力边界

| 项 | 现状 |
| --- | --- |
| 存储桶 | R2 桶 `knowledge-base-assets`，Worker 绑定 `R2_BUCKET` |
| 上传 | `POST /api/assets`（`multipart/form-data`，字段名 `file`，**仅管理员**） |
| 读取 | `GET /api/assets/:id`（**完全公开，不鉴权**，按 UUID 读字节） |
| 列表 / 删除 | `GET /api/assets`、`DELETE /api/assets/:id`（**仅管理员**；被文章引用时返回 409） |
| 格式 | **仅 JPEG / PNG / WebP / AVIF**；SVG / GIF / HTML 一律 415 |
| 大小 | 单张上限 **10MB** |
| 元数据 | 表 `public.assets` **只存元数据**，二进制全在 R2 |
| MCP 工具 | `list_assets` / `set_post_cover` / `upload_image`（**无删除工具**，防误删） |

**能力边界（要记住的三条）**

1. **不做图片转码/压缩**：上传什么字节就存什么字节，**没有缩略图、没有自动 WebP**；
2. **AVIF 尺寸解析不了**：`width`/`height` 恒为 `null`，前端**不能**依赖它做布局；
3. **没有 CDN 自定义域名**：公开地址走 Worker 域名（`/api/assets/<id>`）。

### 5.2 怎么当博客封面（已经能用）

- 在 `frontend/src/routes/PostEdit.jsx` 的封面区上传图片 → 得到链接 →
  「设为封面」写入 `posts.cover_path`；
- 或让 AI 通过 MCP 调 `upload_image` + `set_post_cover`（适合批量）；
- 历史遗留的路径式 `cover_path` 仍可用（见 `docs/storage.md` 第 5 节）。

### 5.3 站长怎么传（三种方式，按场景选）

| 场景 | 方式 | 说明 |
| --- | --- | --- |
| 写一篇文章配一张图 | 网页：`/posts/new` 编辑页的封面区（拖拽/点击） | 最直观 |
| 批量（如给 50 篇旧文补封面） | 对话让 AI 走 MCP：`upload_image` → `set_post_cover` | 需要先有图片文件 |
| 一次传多张 | 现在**没有批量上传 UI**（`docs/storage.md` 第 4 节列为未实现） | 见下条建议 |

### 5.4 建议（P1/P2）

| # | 建议 | 优先级 | 工作量 | 文件 |
| --- | --- | --- | --- | --- |
| 5.4.1 | **上传前自动压缩/转 WebP**（在 `storeImage` 里做，或前端 `canvas` 压缩）：一张 5MB 的图当封面完全没必要 | P1 | M | `backend/src/routes/assets.js`、`backend/src/lib/imageType.js`、`frontend/src/routes/PostEdit.jsx` |
| 5.4.2 | **素材管理页**：现在只有编辑页里的「最近素材」，建议加一个独立素材库页（列表/预览/复制链接/删除），站长不用翻文章找图 | P1 | M | 新建 `frontend/src/routes/Assets.jsx` + `frontend/src/app.jsx` 路由 + `frontend/src/lib/api.js`（`listAssets`/`deleteAsset` **已有**） |
| 5.4.3 | **批量封面回填**（把历史文章缺的封面补齐） | P2 | M | `backend/scripts/` 新增脚本 + `docs/storage.md` |
| 5.4.4 | **R2 生命周期 / 孤儿对象清理**（删除素材已删 R2，但没有定期对账） | P2 | S | `backend/scripts/`、`docs/storage.md` |

### 5.5 存储与费用提示（站长最关心的）

- R2 **免费额度**：每月 10GB 存储、100 万次 A 类操作（写）、1000 万次 B 类操作（读），
  **出网流量免费**（这是 R2 相比其他对象存储最大的优势）。
- 单张 ≤10MB，按博客封面 300KB–1MB 算，10GB 大约能放 **1 万–3 万张**——
  个人站点**基本用不完**。
- ⚠️ **不要**往 R2 放音视频/影视原片：`docs/storage.md` 已明确「禁止存放音视频」，
  项目只存元数据与文本；R2 是给图片（封面/插图）用的。
- 用量随时可在 Cloudflare 控制台的 R2 → Metrics 里看，**建议每月瞄一眼**。

**优先级 P1**（5.4.1 / 5.4.2 是「用起来顺不顺」的关键）。

## 6. 留言墙 / 图片展示 / 时间线 / 画廊（P2，**注意别重复建设**）

### 6.1 先把四个概念分清楚

| 概念 | 是什么 | 与本项目的关系 |
| --- | --- | --- |
| **留言墙** | 访客留言、你回复（需要写权限） | **本项目没有**；要做必须开放写操作（与第 2 节「不开放注册」冲突） |
| **图片展示 / 画廊** | 以图片为主体的浏览页（摄影作品、旅行照） | 已有 R2 素材系统可支撑；`feat/gallery-timeline` 分支**正在做** |
| **时间线** | 按时间倒序的「事件流」（发了一篇文章、收藏了一个仓库…） | `feat/gallery-timeline` 分支**正在做** |
| **画廊/时间流「视图切换」** | 列表的两种排版（网格 vs 时间轴） | **已经存在**：`frontend/src/components/GalleryView.jsx`、`TimelineView.jsx`、`ViewSwitch.jsx` |

### 6.2 别搞混的两件事（最容易重复建设的地方）

1. **「视图切换」≠「画廊模块」**
   `GalleryView` / `TimelineView` 只是**列表排版容器**（每个页面自己传卡片渲染函数），
   它们**不是**内容模块。博客页已经**不再用**视图切换（2026-10-09 改 cosolar 风格后移除，
   见 `docs/removed-features.md`），但组件本身还在被其它页面使用。
   → **不要**因为「分支在做画廊」就去动这两个组件。
2. **「画廊/时间线模块」≠「留言墙」**
   前者是**你自己内容的另一种展示方式**（只读，无需新权限模型）；
   后者是**别人写内容**（要开放写权限、要防垃圾、要审核）。
   两者投入量差一个数量级，**不要混在一个分支里做**。

### 6.3 建议

| 建议 | 说明 | 优先级 |
| --- | --- | --- |
| 6.3.1 画廊/时间线**跟着 `feat/gallery-timeline` 分支走完**，不要另起炉灶 | 该分支已在开发中，避免两套并存 | P2 |
| 6.3.2 **留言墙暂不做** | 与「不开放注册」的策略直接冲突；真想做，先做第 2 节的「邀请制」 | P2（暂缓） |
| 6.3.3 若要做图片画廊，**优先复用 R2 素材**（`public.assets` + `GET /api/assets/:id`），不要再建一套存储 | 复用现成的公开读取能力 | P2 |
| 6.3.4 时间线**优先聚合已有数据**（posts / resources 的 `created_at`），**不要新表** | 数据都在，聚合读取即可（注意别造成「多 Agent 共写一个文件」） | P2 |

**涉及文件（做的时候）**：`frontend/src/components/GalleryView.jsx`、
`frontend/src/components/TimelineView.jsx`、`frontend/src/routes/`（新页面）、
`frontend/src/app.jsx`（路由）、`backend/src/routes/assets.js`（图片源）。

**优先级 P2**（`00-总览` 把「画廊/时间线收尾」放在第三批）。

## 7. 内容运营：AI 写博客 + 草稿/发布 + SEO

### 7.1 AI 写博客 + 同步到 Cloudflare 的流程（P1，工作量 S；主要是规范）

**现有能力**

- MCP 工具 `create_post` / `update_post`（`backend/src/routes/mcp.js`）：
  支持 `title` / `content`（原生 HTML，支持 `katex-inline`、`katex-block`、`mermaid-chart`、
  `chart-2d`、`three-scene` 自定义标签）/ `slug` / `excerpt` / `status` / `is_public` /
  `tag_ids` / `linked_resources`。
- 封面：MCP `upload_image` + `set_post_cover`，或编辑页上传。
- 前端渲染：`frontend/src/components/PostRenderer.jsx`（**写入 DOM 前经
  `frontend/src/lib/sanitizeHtml.js` 白名单清洗**，防存储型 XSS；重型库按需动态 import）。

**建议的固定流程（每次照做）**

```
AI 起草（HTML 正文）
  → create_post，status='draft'、is_public=false   ← 关键：先草稿，别直接发
  → 站长在 /posts/:id 预览（或 PostEdit 的「预览」按钮）
  → 补封面（upload_image + set_post_cover）
  → 确认无误 → update_post：status='published'、is_public=true
```

**三条硬规矩**

1. **AI 一律先写草稿**（`status='draft'`），**绝不直接 `published`**——
   发布是站长的动作，不是 AI 的动作。
2. **正文只存原生 HTML**，不要 Markdown（`docs/requirements.md` 第 7 条）。
3. **自定义标签必须用白名单里的名字**（`katex-inline` 等），否则会被 `sanitizeHtml` 清掉。

### 7.2 草稿与发布状态（P1）

**现状**：`posts.status` ∈ `draft` / `published`，`is_public` 独立控制；
访客只能看 `published + is_public=true`（`docs/public-access.md`）。
`PostEdit.jsx` 已有这两个控件（第 184 行附近）。

**建议**

| # | 建议 | 优先级 | 文件 |
| --- | --- | --- | --- |
| 7.2.1 | 博客列表对**站长**显示草稿角标（`Posts.jsx` 已有 `.cs-draft` 角标，确认对访客不显示） | P1 | `frontend/src/routes/Posts.jsx` |
| 7.2.2 | 加「定时发布」（`published_at` 设为未来时间） | P2 | `backend/src/routes/posts.js`、`supabase/migrations/`（如需新列） |
| 7.2.3 | 加「撤销发布」（已发布 → 转回草稿，`published_at` 保留） | P2 | `backend/src/routes/posts.js` |

### 7.3 SEO（P2，工作量 M）

**现状盘点（这块基本是空白）**

- `frontend/index.html` 的 `<title>` 是**全站固定**的「Dora · 个人知识管理平台」，
  `meta description` 也是全站固定 —— **每篇文章打开都是同一个标题**；
- **没有** `og:` / `twitter:` 分享卡片标签；
- **没有** `robots.txt`、**没有** `sitemap.xml`；
- 单页应用（Preact SPA）+ Cloudflare Pages，搜索引擎抓取本来就不友好。

**建议按顺序做**

| # | 建议 | 说明 | 优先级 | 工作量 |
| --- | --- | --- | --- | --- |
| 7.3.1 | **每篇文章动态改标题** | 在 `frontend/src/routes/PostView.jsx` 里 `document.title = post.title + ' · Dora'`，并同步 `meta description`（用 `excerpt`）。**改动极小、收益最大** | P2 | S |
| 7.3.2 | **加 `robots.txt` + `sitemap.xml`** | `robots.txt` 静态放 `frontend/public/`；`sitemap.xml` 建议由后端动态生成（读已发布文章列表） | P2 | M |
| 7.3.3 | **分享卡片（og:image）** | 用文章封面（`cover_path`）做 `og:image`，微信/群里分享时能出图 | P2 | M |
| 7.3.4 | **预渲染（prerender）已发布文章** | 真正解决 SEO 的方案（Cloudflare Pages 支持构建期预渲染），成本高，**等 7.3.1–7.3.3 做完再说** | P2 | L |

**涉及文件**：`frontend/index.html`、`frontend/public/`（新增 `robots.txt`）、
`frontend/src/routes/PostView.jsx`、`backend/src/routes/posts.js`（若做动态 sitemap）、
`frontend/src/app.jsx`。

> ⚠️ **不要**为了 SEO 引入重型框架（会推翻现有液态玻璃设计语言与按路由分包规范，
> 见 `00-总览` 的「明确不要做」）。
