经复核，泄漏确实存在，且不是孤立一行：

| --- | --- | --- |
| `docs/progress.md` | 管理员邮箱 + 登录密码（凭据表、取 JWT 的 curl 示例共 2 处） | 29 / 42 |
| `docs/storage.md` | R2 账户邮箱 + Cloudflare Account ID | 42 / 42 |

其中 `docs/progress.md` 的凭据表是「项目状态说明」的一部分，从 Phase0 起就存在，因此**几乎贯穿整条历史**。

值得注意的是：上一轮交接文档（`docs/handoff-2026-10-07-refactor.md`）**已经指出过这个问题**并建议清理，但当时只当作「建议项」记录，没有落地 —— 这是本次事故的直接管理原因。

## 2. 处置

### 2.1 止血：轮换凭据（最高优先级）

历史重写**不能**让已经公开的密码重新变安全。唯一有效的动作是让旧凭据失效：

1. 用泄漏的邮箱 + 密码登录生产 Supabase，确认凭据当时**仍然有效**（即泄漏可被直接利用）。
2. 通过 Supabase 用户自助接口修改密码。
3. `POST /auth/v1/logout?scope=global` 全局登出，吊销所有 refresh token（踢掉可能已存在的入侵会话）。
4. 复验：旧密码必须被拒（HTTP 400）、新密码必须可登录（HTTP 200）。

新密码**只保存在密码管理器中**，不写入仓库、不写入文档、不写入命令历史。

### 2.2 脱敏：工作树文档

- 凭据表与 curl 示例改为变量引用（`$ADMIN_EMAIL` / `$ADMIN_PASSWORD`），并注明取值位置。
- 账号 ID、zone id、账号子域一律改为「见控制台 / 见环境变量」。
- 交接文档中「待处理」的安全提示更新为「已处理」。

### 2.3 重写：全部提交历史

- 工具：`git filter-repo --replace-text`（抹掉所有历史版本中的字面量）+ `--email-callback`（作者 / 提交者邮箱统一为 GitHub noreply）。
- 结果：泄漏命中版本数从 **218 降至 0**，邮箱从真实地址统一为 `…@users.noreply.github.com`。
- 重写前已做 `git clone --mirror` 全量备份，可回滚。
- 重写后强制推送 `main`。

### 2.4 预防：让它不能再发生

| 措施 | 位置 | 作用 |
| --- | --- | --- |
| 提交前扫描闸门 | `.githooks/pre-commit` + `git config core.hooksPath .githooks` | 提交那一刻就拦下凭据，不等被人发现 |
| CI 扫描 | `.github/workflows/secret-scan.yml` | push / PR 时扫工作树**与全部历史** |
| 扫描器 | `scripts/check-secrets.mjs` | 无第三方依赖，可本地随时跑 |

扫描器的判定规则（error 级会阻断）：

- JWT 字面量、`ghp_*` / `github_pat_*`、`sk-*`、`AKIA*`、`-----BEGIN … PRIVATE KEY-----`
- 键值形式的明文密码（`"password": "…"`），自动放过 `$VAR` / `<placeholder>` / `your-…` 等示意值
- 连接串内联密码（`postgresql://user:<password>@…`）

warn 级（不阻断，需人工确认）：个人邮箱（gmail / qq / 163 …）、32 位十六进制账号 ID。

### 关于孤立对象

强制推送后，被替换掉的旧提交在 GitHub 上**不会立即消失**：只要知道 SHA，仍能通过
`https://github.com/<owner>/<repo>/commit/<sha>` 读到当时的内容。

彻底清除只有两条路：

1. **删除仓库后重建**（本仓库 0 star / 0 fork / 0 issue / 0 PR，代价极小；但需重新配置
   Actions secrets，Cloudflare 侧的 Pages / Workers 项目不受影响）。
2. **联系 GitHub Support** 请求回收不可达对象。

由于**密码已经轮换**，孤立对象里的凭据已经没有利用价值，因此这一步属于「锦上添花」而非必需。
是否执行由仓库所有者决定。

## 4. 教训

1. **凭据不进仓库，也不进文档。** 文档只写变量名与取值位置，值放在 `.env.local`（已 gitignore）或密码管理器。
2. **「建议清理」不等于「已清理」。** 上一轮已经把这个问题写进交接文档，但因为没有落到动作项，问题原地保留了 6 天并随历史发布。安全类待办必须有 owner 与截止时间。
3. **重写历史不等于修复泄漏。** 顺序必须是：先轮换凭据（止血）→ 再脱敏 → 最后重写历史。反过来做只会得到「看起来干净但仍可被利用」的假安全感。
4. **仓库是私有也不代表安全。** 每个有读权限的人、每个本地克隆、每次 CI 日志、每份离线备份都是泄漏面。
