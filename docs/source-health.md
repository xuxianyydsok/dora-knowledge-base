# 源健康中心（Source Health）

> 影视采集源 + 音乐音源的统一可用性观测。第一版（2026-10-10，分支 `feat/source-health-console`）。

## 1. 它解决什么问题

影视与音乐都是「多源聚合」：一部片/一首歌搜不出来，可能是**这个源挂了**，
而不是真的没有。此前只有影视页抽屉里一条粗糙的探活（`checkMaccms` 只发一次
`ac=videolist&wd=测试` 看有没有响应），既没覆盖音乐，也没参与搜索决策。

本模块做三件事：

1. **统一观测**：把影视与音乐源的可用性收敛成一份结构，一页看清谁挂了、为什么。
2. **自动避让**：搜索时跳过已知 `down` 的源、把 `degraded` 的源排到后面，减少无谓等待。
3. **如实标注**：只声明「可验证」的能力，试听源如实标注为试听，绝不冒充无损/高音质。

## 2. 统一数据结构

`GET /api/sources/health` 返回：

```jsonc
{
  "generated_at": "2026-10-10T08:00:00.000Z", // 本次探测时间（两部分取较早者）
  "cached": false,                            // 是否来自缓存
  "ttl_ms": 90000,                            // 本次缓存 TTL
  "summary": {
    "total": 12, "ok": 9, "degraded": 2, "down": 1,
    "movie": { "total": 6, "ok": 5, "degraded": 1, "down": 0 },
    "music": { "total": 6, "ok": 4, "degraded": 1, "down": 1 }
  },
  "sources": [
    {
      "key": "guangsu",                 // 内部键（影视：源 key；音乐：gdstudio:netease / meting:qijieya:netease …）
      "name": "光速资源",                // 中文展示名
      "kind": "movie",                  // movie | music
      "status": "ok",                   // ok | degraded | down
      "ok": true,                       // status === 'ok'
      "latency_ms": 312,                // 探测耗时
      "checked_at": "2026-10-10T08:00:00.000Z",
      "error": null,                    // 失败 / 降级原因（人话）
      "capabilities": {                 // 只放「可验证」的能力
        "search": true, "detail": true, "play": true
      },
      "notes": null                     // 例如「仅 30 秒试听（非完整曲目）」
    }
  ],
  "note": null                          // 无数据时给出「暂无数据，请稍后由管理员刷新」
}
```

### 状态判定规则（硬性）

| 状态 | 影视 | 音乐 |
| --- | --- | --- |
| `ok` | 搜索有结果 + 详情可取 + 详情含可播放地址 | 搜索有结果 + 确实取到可播放地址 |
| `degraded` | 能连通但受限：搜索空结果 / 详情验证失败 / 无播放地址 | 空结果 / 试听源（iTunes、Deezer）/ 未取到播放地址 |
| `down` | 超时 / 连接失败 / HTTP 错误 / 返回结构非法 | 同上 |

- **绝不允许**把「未验证」写成 `ok`。
- **绝不允许**把「30 秒试听」写成无损 / 高音质。iTunes / Deezer 恒为 `degraded` +
  `trial_only: true`，`play` 为 `false`，`notes` 固定为「仅 30 秒试听（非完整曲目）」。
- 影视「搜索成功但详情失败」是 `degraded`，**不是** `down`（搜索仍能用）。

## 3. 探测实现

- 每个源**独立探测**：影视并发跑「搜索（必做）→ 详情（能力验证）」；
  音乐并发跑 GD音乐台（netease / joox）、Meting（逐实例逐平台）、Audius、iTunes、Deezer。
- **单源超时 + 全局预算**双保险（`probeEntries`）：
  - 影视：单源 6s、整体预算 8s；音乐：单源 8s、整体预算 10s。
  - 全局预算耗尽时，未返回的源统一标 `down`，原因写明「探测超时（Nms 总预算内未返回）」。
  - 单个源抛错 / 超时**不会**拖垮全局，整体一定返回。
- 音乐 `play` 能力**只有在确实解析出可播放地址时才为 true**：
  GD 会实际调一次 `types=url`；Meting 检查结果是否自带取流地址；
  Audius 检查 `is_streamable`；iTunes / Deezer 不取流、恒 `play: false`。

## 4. 缓存与并发去重

- 模块内短 TTL 缓存：影视 **90s**、音乐 **120s**，可用 `env.SOURCE_HEALTH_TTL_MS` 统一覆盖。
- 同一 isolate 内并发请求**去重**：进行中的探测 Promise 被复用，打开面板不会打爆免费上游。
- **新鲜缓存**（TTL 内）命中时 `cached: true`，并保留上次 `generated_at`。
- **过期缓存绝不用于源过滤**（关键语义）：
  - 访客 / 搜索路径（`allowProbe: false`）在缓存**已过期或不存在**时，**不发任何探测**，
    也**不返回过期数据**——`sources` 返回空数组，`cached: false`，`empty: true`，`stale: true`，
    并给出 `stale_at`（过期缓存的探测时间，便于诊断 / 前端提示）。
  - 这样搜索会按「无数据」处理 → 冷启动式**全量尝试**，不会被一次瞬时的 `down` 无限期沿用。
  - 只有**管理员路径**（`allowProbe: true`）会重新探测并覆盖缓存。
- 响应字段含义：
  | 字段 | 含义 |
  | --- | --- |
  | `cached` | 是否命中**新鲜**缓存（影视、音乐两部分都命中才为 `true`） |
  | `stale` | 是否存在**已过期**缓存（过期数据未返回，仅用于提示） |
  | `stale_at` | 过期缓存的探测时间（ISO 字符串）；无过期缓存时为 `null` |
  | `note` | 无可用数据时的人话提示（「暂无数据，请稍后由管理员刷新」） |
- 支持 `?refresh=1` 强制刷新，**仅管理员**可用（见下节）。
- ⚠ TTL 缓存是 **per-isolate** 的：Cloudflare Workers 会横向扩展多个 isolate，
  每个 isolate 各有一份缓存，因此实际上游探测次数略多于「全局一份」。

## 5. 鉴权与「访客不触发探测」

新增聚合接口 `GET /api/sources/health`：

| 身份 | 行为 |
| --- | --- |
| **管理员** | 全量探测；可用 `?refresh=1` 强制刷新 |
| **普通用户 / 未登录访客** | **绝不触发上游探测**，只读**新鲜**缓存；缓存为空**或已过期**时返回空 `sources` + `note`（过期时另带 `stale`/`stale_at`），前端提示「请稍后由管理员刷新」 |

> 选择的是方案 (b)：访客只读缓存（体验更好），但**保证访客请求绝不发起新的上游探测**。
> 实现上由 `getSourceHealth(env, { allowProbe: false })` 保证——该分支只返回**新鲜**缓存，
> 过期/缺失时返回空数据，**不做任何网络请求**。

前端 `/sources` 页：**非管理员不显示「刷新」按钮**（且 `load()` 内部对非管理员强制 `refresh`
退化为普通只读加载），因此不会出现「点了刷新、其实后端只返回缓存却提示成功」的假报成功。

既有接口 `GET /api/movies/sources/health` **保留兼容**（影视页抽屉仍在用），
但改为读**同一份**健康缓存，避免两条路径各探一遍；其鉴权行为与现状一致
（`requireAuth`，访客模式下由 `guestContext` 放行，同样只读缓存）。

## 6. 健康结果如何参与搜索 / 播放

- **影视**：`searchMaccmsAll()` 搜索前读一次健康缓存（`allowProbe: false`，不额外探测）：
  - 跳过 `status === 'down'` 的源；
  - `degraded` 的源仍参与，但排在 `ok` / 未知源之后（`rankSources`）。
  - **冷启动安全**：健康数据缺失时 `rankSources` 不剔除任何源、不改顺序，
    首次请求照常全量尝试。
  - 合并结果时**不破坏「相关度第一」排序**：健康只调整「哪些源参与、以什么顺序发起」，
    最终仍按 `titleRelevance` 排；健康不会把不相关的条目顶到前面。
- **音乐**：`fetchMusicMeta()` 同理，读健康缓存后跳过已知 `down` 的音源；
  试听源（iTunes / Deezer）的结果保留但带 `trial_only: true` 标注，前端据此显示「试听」。
  `musicScore` 排序逻辑**保持不变**，健康只做「过滤 + 同级打破」，不重排掉正片。
- **纯函数**：`rankSources(sources, healthMap)` / `isSourceUsable(health)` 放在
  `backend/src/lib/sourceHealth.js`，便于离线单测。

## 7. 前端

- 新页面 `frontend/src/routes/SourceHealth.jsx`，路径 `/sources`，
  `ProtectedRoute` **不带 `guest`**（需要登录）。
- 入口在 `Layout.jsx` 的「更多」下拉里，**仅管理员可见**（`isAdmin`）。
- 内容：总览卡（总数 / 可用 / 降级 / 不可用，分影视、音乐三组）、
  分类筛选（全部 / 影视 / 音乐）、「刷新」按钮（`?refresh=1`）、每源一行
  （状态点、中文名、类型标签、状态、延迟、能力标签、检测时间、失败原因 / 备注）。
- 顶部醒目说明：**「健康是瞬时观测，不保证永久可用」**。
- 影视页抽屉底部加了「查看完整源状态」链接（仅管理员）。

## 8. 版权 / 合规边界

- 本模块**只治理项目已有 / 用户自配的源**，不集成来源不明的盗版接口，不为「数量」新增源。
- 只抓取元信息与播放地址字符串，**不下载视频 / 音频文件，后端不转发流媒体**。
- 试听源如实标注，**不宣称无损 / 高音质**；能力字段只放「可验证」的项，
  读不到的码率 / 清晰度一律留空，不编造。
- 健康探测本身也走真实请求，遵守各上游的既有使用方式（固定探测词、短 TTL、并发去重），
  避免给免费上游造成压力。

## 9. 已知限制

1. **瞬时观测**：一次探测成功不代表永久可用；上游会随时波动、限频。
2. **per-isolate 缓存**：见第 4 节。
3. **未做真实网络端到端验证**：本机无法连真实上游 / Supabase，只有纯离线单测覆盖纯函数与调度逻辑。
4. 音乐源若声明 `play` 但取流地址是**会过期的签名直链**（如 GD），
   探测通过不代表播放时仍有效；点播时由 `/api/music/stream` 现取。
